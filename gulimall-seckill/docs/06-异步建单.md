# 业务流程 06：异步建单

## 一、设计思路

- 预扣记录与建单消息同事务写入：Redis 原子预扣成功后，在同一个本地事务里插入 `sms_seckill_order(status=0)` 和 `mq_message(status=0)`，事务提交后再投递，避免“扣了库存但消息没落库”。
- 消费端采用手动 ack：只有走到明确终态才签收；未知异常交给 `MqRetryService` 延迟重试，防止消息在异常时被静默丢掉。
- 幂等由三层条件写保证：`sms_seckill_order.status` 只允许从 `WAIT_BUILD` 推进，`oms_order.order_sn` 与 `wms_ware_order_task.order_sn` 各有唯一键，重复消息不会重复建单。
- 建单只做库存口径转换：`stock_locked + q`、`seckill_stock_locked - q`，总占用不变；真实 `stock` 扣减留到支付成功，避免未付款就减库存。
- 明确业务失败才回补：先把秒杀单从 `0` 条件更新为 `3`，再执行 Redis Lua 回补库存与限购；Lua 用 `seckill:release:{orderSn}` 标记防重复，库存 key 不存在时返回 `-1`，不凭空造库存。
- 响应超时不等同于建单失败：order 返回失败时先查订单状态，订单已存在则回填成功，避免误回补。
- order 侧用 `@GlobalTransactional` 包裹订单落库与 ware 库存转换，任一步失败整体回滚；消费端失败仍由消息重试兜底。
- 定时对账覆盖消息丢失、消费者宕机和状态未回写三类缺口，超过重试上限后主动回补并置为失败。

关键数据：`sms_seckill_order` 状态 `0` 待建单、`1` 已建单、`3` 建单失败；Redis 键 `seckill:stock:{sessionId}:{skuId}`、`seckill:user:count:{sessionId}:{skuId}`、`seckill:release:{orderSn}`；工作单 `biz_type=1`、`task_status=1`。

消息重试次数保存在消息头 `mq_retry_count`，秒杀单的补偿次数保存在 `build_retry_count`，两者独立排查。
消息体与预扣记录字段同源，消费端不需要再查会员、商品或地址快照。

## 二、主要功能描述

### 触发与前置

- 触发：第 04 步提交抢购在 Redis 预扣成功后写入可靠消息，事务提交后投递到 `gulimall-seckill-order-create-queue`。
- 前置：`sms_seckill_order` 已有一行 `status=0` 且字段完整；RabbitMQ 延迟插件、order、ware、Seata TC 均可用；收货地址属于下单会员；ware 有足够的 `seckill_stock_locked`。

### 处理内容

- 消费 `SeckillOrderCreateMessage`，按 `orderSn` 查预扣单并校验状态。
- 调用 order 内部接口 `/internal/order/seckill/create`，在全局事务内幂等写 `oms_order`、`oms_order_item`，再调 ware 把活动锁定转为订单锁定。
- 成功时把秒杀单 `0 → 1`，回填 `order_id`、`pay_amount`；明确失败时 `0 → 3`，写 `fail_reason` 并回补 Redis。
- 网络、超时、数据库等未知异常按 10s/30s/60s 延迟重试，3 次用尽后进入死信归档。

### 不处理内容

- 不扣真实库存 `stock`，不发起支付，不处理用户取消、超时关闭和支付成功。
- 不依赖用户会话，会员信息全部来自消息体。
- 不使用 `SeckillStockOperation` 幂等，幂等键是 `order_sn`。

### 最终结果

| 结果 | 秒杀单 | 订单与工作单 | Redis |
|---|---|---|---|
| 成功 | `status=1`，回填 `order_id`、`pay_amount` | `oms_order status=0`、`source_type=2`；工作单 `1/1` | 不回补 |
| 明确失败 | `status=3`，写 `fail_reason` | 全局事务回滚 | 库存 `+q`、限购 `-q` |
| 未知异常 | 仍为 `0` | 由全局事务决定 | 不回补，等待重试 |

### 异常与降级

- 消息反序列化失败或远程调用异常：进入 `handleFailure`，重试 3 次后死信，秒杀单保持 `0`，由对账任务继续处理。
- 地址不属于会员或库存不足：order 抛业务异常，Seata 全局回滚，消费端按业务失败回补 Redis。
- 预扣记录不存在：记 error 后 ack，不再重试；状态已推进：直接 ack，保持幂等。
- 死信归档失败：不 ack，消息留在死信队列，等待人工处理。
- 活动结束导致 Redis 库存 key 已删：回补返回 `-1`，不凭空创建库存。
- Seata TC 不可用：order 建单失败，消息按 10s/30s/60s 重试，恢复后可继续。

## 三、执行顺序

1. `MqMessageService#sendReliable`：本地事务写 `mq_message(status=0)`，提交后投递建单交换机，投递失败由补偿任务重发。
2. `SeckillOrderCreateListener#onCreate`：手动 ack 消费，按字节反序列化 `SeckillOrderCreateMessage`。
3. 同上：按 `order_sn` 查 `sms_seckill_order`；记录不存在时记 error 并 ack；状态不是 `WAIT_BUILD` 时直接 ack。
4. 同上：把消息转成 `SeckillOrderCreateVo`，调用 `OrderFeignClient#createSeckillOrder`。
5. `SeckillOrderInternalController#create`：转发到 `OrderServiceImpl#createSeckillOrder`，开启 `@GlobalTransactional`。
6. `OrderServiceImpl#createSeckillOrder`：校验参数，按 `order_sn` 查 `oms_order`；已存在则返回旧订单并标记重复。
7. 同上：`MemberReceiveAddressFeignClient#getAddressById` 校验地址归属，地址不属于该会员时抛 `ORDER_ADDRESS_INVALID`。
8. 同上：按 `seckillPrice × quantity` 计算 `payAmount`，运费与优惠为 0，写入 `oms_order`（`source_type=2`、`status=0`、`note=秒杀订单`）和 `oms_order_item`。
9. 同上：调用 `WareFeignClient#lockSeckillOrderStock`，进入 ware 的活动锁定转订单锁定。
10. `WareSkuController#lockSeckillOrderStock` → `WareSkuServiceImpl#lockSeckillOrderStock`：按 `order_sn` 查工作单；已有秒杀工作单直接返回，工作单属于普通订单则抛错。
11. 同上：写入 `wms_ware_order_task`，`task_status=1`、`biz_type=1`、`seckill_session_id`、`member_id`，用唯一键占住订单号。
12. 同上：条件更新 `wms_ware_sku`，`stock_locked + q`、`seckill_stock_locked - q`，同时要求活动锁定和可用库存足够。
13. 同上：更新 0 行时抛“秒杀库存不足”，本地事务回滚并触发 Seata 全局回滚；成功时写明细 `lock_status=1`。
14. `OrderServiceImpl#createSeckillOrder`：返回 `orderId`、`payAmount`、`status`，全局事务提交。
15. `SeckillOrderCreateListener#onCreate`：order 返回 `code=0` 时调用 `SeckillOrderServiceImpl#onBuildSuccess`。
16. `SeckillOrderServiceImpl#onBuildSuccess`：条件更新 `status 0→1` 并回填 `order_id`、`pay_amount`，随后 ack。
17. `SeckillOrderCreateListener#orderExists`：order 返回失败时查询订单状态；订单已存在则按成功回填并 ack。
18. `SeckillOrderServiceImpl#failAndRelease`：条件更新 `status 0→3`、写 `fail_reason`；更新 0 行说明已被其它流程处理，直接返回。
19. `SeckillStockServiceImpl#releaseReservation`：Lua 回补 `seckill:stock`、`seckill:user:count`，写 `seckill:release`；返回 `0` 表示已回补，`-1` 表示库存 key 不存在。
20. `SeckillOrderCreateListener#onCreate`：业务失败回补完成后 ack，不进入消息重试。
21. `MqRetryService#handleFailure`：反序列化、网络、数据库等异常按 `mq_retry_count` 延迟重发 10s/30s/60s，3 次用尽后投死信并 ack。
22. 异常分支：重发或投死信本身失败时执行 `basicNack(requeue=false)`，由队列死信交换机兜底。
23. `SeckillOrderReconcileTask#reconcileWaitingBuild`：每分钟扫超过 5 分钟仍为 `WAIT_BUILD` 的单；已建单则回填，未建且补偿次数小于 5 时重发消息，超限调用 `failAndRelease` 回补。
24. 分支：地址校验失败或 ware 库存不足时，order 全局事务回滚，消费端按业务失败调用 `failAndRelease` 并 ack。
25. 分支：order 或 ware 不可用导致 Feign 异常时，消息进入重试；恢复后重试成功，秒杀单 `0→1`；重试用尽则进死信，由对账任务继续处理。
