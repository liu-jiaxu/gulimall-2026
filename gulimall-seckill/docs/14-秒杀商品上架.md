# 业务流程 14：秒杀商品上架

## 一、设计思路

- 上架只把场次、关联和商品信息投影到 Redis，不修改任何业务表，场次状态流转由 MQ 负责。
- 商品信息统一写入 Hash `seckill:session:{sessionId}:skus`，field 为 `skuId`，value 为 `SeckillSkuVo` JSON，TTL 设为 `end_time + 1 天`。
- 上架范围与前台查询保持一致：`status = 1`、`seckill_state IN (0,1)`、`end_time >= now`、`start_time <= now + 3 天`，避免“页面看得到但没有上架”。
- `randomCode` 优先沿用旧 Hash 中的值，只有缺失或解析失败才重新生成，避免已经展示给用户的码因重新上架失效。
- 库存 key 使用 `SETNX` 只补不覆盖，防止把已经扣减的剩余库存重置回秒杀总量。
- product 不可用时跳过该 SKU 并保留旧 Hash 字段，单个 SKU 失败不影响同场其他商品。
- 关联新增或修改成功后，coupon 通过 Feign 调 `/seckill/refresh` 只重建指定 SKU 的 Hash 字段。
- 定时任务没有分布式锁，多实例会重复执行，但 Hash 覆盖和 `SETNX` 写入本身幂等。

## 二、主要功能描述

**触发动作**

- 每天 03:00，`SeckillSkuScheduled` 自动触发全量上架。
- 运维或测试通过 `POST /seckill/upload` 手动触发全量上架。
- 后台关联商品新增或修改成功后，coupon 调 seckill `/seckill/refresh` 触发单商品刷新。

**前置条件**

- `sms_seckill_session` 中存在启用场次，时间完整，且处于上架时间窗口内。
- `sms_seckill_sku_relation` 中存在该场次关联，且 `ware_id` 已写入。
- product 服务可访问，Redis 可用，seckill 启动类已开启定时任务。

**Redis 数据结构**

- `seckill:session:{sessionId}:skus`：Hash，field 为 `skuId`，value 为 `SeckillSkuVo` JSON。
- `seckill:stock:{sessionId}:{skuId}`：String，值为剩余秒杀库存，只在首次写入时设置 TTL。
- `gulimall:ware:stock:{skuId}`：普通可售库存缓存，由上架之外的库存操作刷新。

**降级行为**

- product 超时或返回失败时，Feign fallback 返回空，SKU 被跳过，旧 Hash 字段保留。
- Hash 写入异常会中断整次上架，已写入的场次保留，后续场次等待下次执行。
- 库存 key 已存在时不刷新 TTL，场次时间延长后旧 key 仍按原结束时间过期。
- 库存 key 被误删时，上架会按秒杀总量补回，结果可能高于真实剩余。

**做什么**

- 全量上架：查场次和关联，逐个查 product，组装 `SeckillSkuVo`，写商品 Hash，必要时补库存 key。
- 单商品刷新：只处理一个 `sessionId + skuId`，重建该 SKU 的 Hash 字段，不影响同场其他商品。
- 删除关联时由 coupon 直接 HDEL 对应 Hash 字段，失败只记日志。

**不做什么**

- 不读取或修改 `sms_seckill_session`、`sms_seckill_sku_relation` 的业务字段。
- 不锁库存、不释放库存，库存锁定发生在后台关联商品流程。
- 不覆盖已经存在的秒杀库存 key，不删除已不在关联表中的 Hash 字段。
- 不发送场次开始或结束 MQ。

**结果状态**

- 场次商品 Hash 写入成功，TTL 为 `end_time + 1 天`；缺失的库存 key 被补齐，已有 key 保持不变。
- product 查不到的 SKU 不出现在新 Hash 中，旧字段继续保留到 TTL 到期或关联删除。
- 手动接口返回成功只表示方法执行完成，单 SKU 跳过情况需要查看日志。

## 三、执行顺序

1. `SeckillSkuScheduled#uploadSeckillSku`：每天 03:00 调用 `uploadSeckillSkuLatest3Days`。
2. `SeckillController#upload`：手动 `POST /seckill/upload` 调用同一上架方法。
3. `SeckillSkuServiceImpl#uploadSeckillSkuLatest3Days`：查 `sms_seckill_session`，条件为启用、状态 0/1、结束时间未过、开始时间在未来 3 天内。
4. `uploadSeckillSkuLatest3Days`：逐场次跳过时间不完整或 `end_time + 1 天` 已过期的场次，并计算该场次 TTL。
5. `uploadSeckillSkuLatest3Days`：按 `promotion_session_id` 查 `sms_seckill_sku_relation` 获取全部关联。
6. `SeckillSkuServiceImpl#getProductSku`：调 product `/product/skuinfo/info/{skuId}`；返回空或异常时跳过该 SKU。
7. `SeckillSkuServiceImpl#buildSkuVo`：用场次、关联和商品数据组装 `SeckillSkuVo`，写入价格、数量、限购、排序和时间。
8. `SeckillSkuServiceImpl#resolveRandomCode`：解析旧 Hash JSON，存在 `randomCode` 则沿用，否则生成新 UUID。
9. `uploadSeckillSkuLatest3Days`：序列化 `SeckillSkuVo`；单个序列化失败只跳过该 SKU。
10. `uploadSeckillSkuLatest3Days`：`seckill_count > 0` 时用 `setIfAbsent` 写 `seckill:stock:{sessionId}:{skuId}`，已存在则不覆盖值和 TTL。
11. `uploadSeckillSkuLatest3Days`：场次内至少一个 SKU 成功时，`putAll` 写商品 Hash 并 `expire` 整场 TTL。
12. `uploadSeckillSkuLatest3Days`：记录“上架完成：场次=N 商品=M”日志，不逐场次捕获 Redis 异常。
13. `SeckillSkuRelationController#refreshSkuCache`：coupon 在关联新增或修改成功后通过 Feign 调 `/seckill/refresh`。
14. `SeckillController#refresh`：接收 `sessionId` 和 `skuId`，调用 `refreshSessionSku`。
15. `SeckillSkuServiceImpl#refreshSessionSku`：校验参数、场次时间、关联存在和 TTL，任一不满足直接返回。
16. `SeckillSkuServiceImpl#refreshSessionSku`：调 `getProductSku`；product 不可用时保留旧 Hash，不删除也不重建。
17. `SeckillSkuServiceImpl#refreshSessionSku`：读旧 Hash 沿用 `randomCode`，HSET 单个 field 并重置整场 TTL；不写库存 key。
18. `SeckillSkuRelationServiceImpl#deleteSessionSku`：coupon 删除关联时直接 HDEL 对应 Hash 字段，Redis 失败只记日志。
19. `SeckillSkuServiceImpl#cacheSku`：前台查询发现 Hash 缺失时回源数据库和 product，回填单个字段，不创建库存 key。
