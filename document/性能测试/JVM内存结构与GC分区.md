# JVM 内存结构与 GC 分区（JDK 21）

> 调 JVM 参数之前，必须先搞清三件事：
> **哪块内存归哪个参数管**、**JDK 21 默认用什么垃圾收集器**、**它的分区模型和老教程有什么不同**。
>
> 具体的启动参数配置、验证命令、调优流程见《性能测试-常见问题手册.md》§2.1.1。

---

## 一、JVM 内存有哪些区域

很多人以为"JVM 内存 = 堆"，其实堆只是一部分。**调参前先分清哪块内存归哪个参数管**：

```
┌───────────────────────── JVM 进程占用的内存 ─────────────────────────┐
│                                                                      │
│  ┌──────────── 堆 Heap ────────────┐    ┌───── 非堆 Non-Heap ─────┐  │
│  │                                 │    │                          │  │
│  │  新生代 Young + 老年代 Old        │    │  Metaspace（类元数据）     │  │
│  │  ↑ -Xms / -Xmx 控制              │    │  ↑ -XX:MetaspaceSize     │  │
│  │                                 │    │    -XX:MaxMetaspaceSize  │  │
│  │                                 │    │                          │  │
│  │                                 │    │  代码缓存 Code Cache      │  │
│  │                                 │    │  ↑ -XX:ReservedCodeCache │  │
│  │                                 │    │                          │  │
│  │                                 │    │  直接内存 Direct Memory   │  │
│  │                                 │    │  ↑ -XX:MaxDirectMemory   │  │
│  │                                 │    │    (默认 = -Xmx)          │  │
│  │                                 │    │                          │  │
│  │                                 │    │  线程栈 × 线程数           │  │
│  │                                 │    │  ↑ -Xss（默认 1MB/线程）   │  │
│  └─────────────────────────────────┘    └──────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────┘
```

> ⚠️ **`-Xmx4g` ≠ JVM 只占 4GB。**
>
> 实际物理内存 = 堆 + Metaspace（几十~几百 MB）+ **直接内存（默认等于 `-Xmx`！）** +
> 线程栈（400 线程 × 1MB = 400MB）+ 代码缓存。
>
> **`-Xmx4g` 的 JVM 峰值可能吃掉 6GB 以上** —— 规划服务器内存时必须算上这部分，
> 否则容易出现"堆还没满，进程却被系统 OOM Killer 杀了"。

## 二、堆内分代：对象怎么流转

```
┌─────────────────────────────── JVM 堆（-Xms / -Xmx 控制）───────────────────────────────┐
│                                                                                        │
│  ┌─────────────────── 新生代 Young ───────────────────┐    ┌───── 老年代 Old ─────┐    │
│  │                                                    │    │                      │    │
│  │   ┌──────────┐        ┌──────┐        ┌──────┐     │    │                      │    │
│  │   │          │        │      │        │      │     │    │                      │    │
│  │   │   Eden   │ ─────→ │  S0  │ ←────→ │  S1  │     │───→│   长期存活的对象      │    │
│  │   │          │        │      │        │      │     │    │                      │    │
│  │   └──────────┘        └──────┘        └──────┘     │    │   超大对象直接进来     │    │
│  │        ↑              └─ Survivor 两个，总有一个是空的 ┘    │                      │    │
│  │        │                                  │         │    └──────────────────────┘    │
│  └────────┼──────────────────────────────────┼─────────┘               ↑              │
│           │                                  │                         │              │
│      新对象先分配在这                  Minor GC 后存活对象          年龄达阈值        │
│                                       在 S0/S1 之间来回复制      （默认 15）搬过来     │
└────────────────────────────────────────────────────────────────────────────────────────┘
                 │                                              │
                 ↓                                              ↓
          Minor GC / Young GC                              Full GC
          · 只扫新生代                                     · 扫整个堆（含老年代）
          · 频繁但极快（几毫秒 ~ 几十毫秒）                   · 少但慢（几百毫秒 ~ 几秒）
          · 绝大多数对象在这就被回收（"朝生夕死"）             ★ 频繁 Full GC = 有问题
```

**分代设计的依据 —— "弱分代假说"：**

> 统计上 **98% 以上的对象活不过第一次 GC**。

所以把新对象放一小块区域（Eden），用低成本快速回收；只有少数活下来的才"晋升"到老年代。
这样每次 GC 只需要扫一小块内存，而不是整个堆 —— 这是 JVM 性能的核心机制。

**两个 GC 的区别：**

| | Minor GC / Young GC | Full GC |
|---|---|---|
| 扫描范围 | 只扫新生代 | 整个堆（含老年代） |
| 频率 | 频繁（几秒一次都可能） | 少 |
| 停顿 | 极短（几毫秒 ~ 几十毫秒） | 长（几百毫秒 ~ 几秒） |
| 影响 | 基本无感 | **会卡住所有业务线程** ★ |

> ⚠️ **上面这张图是"逻辑模型"** —— G1 和传统 GC **都遵循**这套晋升逻辑。
> 两者的差别在于**物理上怎么组织这些区域**、以及**老年代什么时候被回收**，见 §三。

## 三、JDK 21 默认是 G1，和传统分代 GC 的三大区别

**JDK 9 起 G1 就是默认垃圾收集器**，到 JDK 21 依然是。

先明确一个最容易搞错的点：

> **G1 并没有取消 Eden / Survivor / Old** ——
> 对象晋升的逻辑（Eden → Survivor → Old）**和传统 GC 是一样的**。
> G1 改的是「这些区域在物理内存上怎么组织」和「老年代什么时候被回收」。
>
> 所以"G1 和传统 GC 不一样"说的是下面三个层面的差别，**不是晋升逻辑变了**。

### 3.1 区别一：内存组织 —— 从「固定的连续空间」到「动态的 Region 集合」

**传统 GC（Parallel / CMS）：区域位置和大小相对固定**

```
整个 Heap
┌──────────────────────────────────────┐   ┌─── Old（固定大小）───┐
│  Young（固定大小）                     │   │                      │
│  ┌──────────┬──────┬──────┐            │   │                      │
│  │   Eden   │  S0  │  S1  │            │   │                      │
│  └──────────┴──────┴──────┘            │   │                      │
└──────────────────────────────────────┘   └──────────────────────┘
     ↑ 这三块是物理上连续的固定空间，位置和大小一开始就定死
```

**G1：堆被切成约 2048 个等大 Region，角色动态分配**

```
整个 Heap
┌────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┐
│ E  │ E  │ E  │ S  │ S  │ O  │ O  │ O  │ O  │ H  │ 空 │ 空 │
└────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┘
  E = Eden   S = Survivor   O = Old   H = Humongous（超大对象）   空 = 尚未分配

· 没有任何 Region 被【永久指定】为"这个永远是 Eden / S0 / Old"
· 它们只是【当前这一时刻】扮演的角色
· Region 可以分散在整个 Heap 中，不要求连续
```

**下一轮 GC 后，角色可能完全变了：**

```
GC 前：                         GC 后：
┌────┬────┬────┬────┐          ┌────┬────┬────┬────┐
│ E  │ E  │ S  │ O  │    →     │ 空 │ 空 │ S  │ O  │
├────┼────┼────┼────┤          ├────┼────┼────┼────┤
│ O  │ 空 │ E  │ O  │    →     │ O  │ S  │ 空 │ O  │
└────┴────┴────┴────┘          └────┴────┴────┴────┘

原来的 Eden Region 里对象被回收/搬走后，Region 变回"空闲"，
下一轮可以重新被分配成 Eden、Survivor 或 Old。
```

**一句话**：不是取消了 Eden/Survivor/Old，而是这些区域从**「固定的连续空间」**变成了**「动态的 Region 集合」**。

### 3.2 区别二：G1 的 Young GC 是「Evacuation（疏散）」式的

不管传统 GC 还是 G1，Young GC 做的事都一样：

```
   Young Region（Eden + Survivor）
              ↓
          Young GC
              ↓
        找出存活对象
              ↓
     Evacuation（疏散：把存活对象【复制】到新地方）
              ↓
        ┌─────┴─────┐
        ↓           ↓
  新的 Survivor     Old
    Region          Region
        ↓
   原来的 Region 整块释放
```

> 叫 **Evacuation（疏散）** 而不是"清理"，是因为它的做法是
> **把活的对象搬走，然后整块 Region 直接释放** —— 不需要逐对象清理。
> 这种"复制式回收"对**存活对象很少**的新生代极其高效（正好符合"98% 对象朝生夕死"）。

### 3.3 区别三 ★ **G1 除了 Young GC，还有 Mixed GC**

**这是 G1 最核心的差别**，也是它名字里 "Garbage First" 的由来。

**传统 GC 怎么收老年代：**

```
Young GC 只收 Young
        ↓
Old 一直攒
        ↓
攒满了 / 条件触发
        ↓
Full GC —— 一次性回收【整个老年代】     ← 停顿很长（可能几秒）
```

**G1 的 Mixed GC：**

```
Mixed GC 同时回收：
    Young Region  +  【部分】Old Region

              ↓ Evacuation

        释放这些 Region

┌────┬────┬────┬────┬────┬────┬────┐
│ E  │ E  │ S  │ O  │ O  │ O  │ 空 │
└────┴────┴────┴────┴────┴────┴────┘
              └────┴────┘
         挑「垃圾最多、回收收益最高」的 Old Region
         （不是把所有 Old Region 都收）
```

**对比：**

| | 传统 GC | G1 |
|---|---|---|
| 老年代什么时候收 | **攒满了一次性收** | **增量地、分批收** |
| 收哪些 Old Region | 全部 | **挑垃圾最多的那部分**（收益优先） |
| 单次停顿 | 很长 | **可控**（受 `MaxGCPauseMillis` 约束） |
| 触发方式 | 只在 Full GC | **Mixed GC**（Young + 部分 Old） |

> G1 在后台维护每个 Region 的"垃圾占比"，Mixed GC 时优先挑垃圾多、回收快的 Region 下手。
> 这样**不用等整个老年代满了才收**，停顿自然就短了 ——
> **这就是 G1 能做到"停顿可预测"的根本原因。**

### 3.4 补充概念：Evacuation Failure（疏散失败）

**先纠正一个常见的不准确说法：**

> ❌ "Survivor 放不下了，就全部丢进老年代"

**官方描述是**：Young 区的 Eden/Survivor 对象，**根据年龄（和晋升策略）**被复制到 Survivor Region 或 Old Region：

```
   Young GC
       ↓
   对象存活
       ↓
  根据【年龄】判断
       ├──→ 年龄未到阈值 → 复制到 Survivor Region
       └──→ 年龄达到阈值 → 复制到 Old Region
```

**年龄阈值**由 `-XX:MaxTenuringThreshold` 控制（G1 默认 **15**），**不是**"Survivor 满了就赶过去"。

**那 Survivor 真的放不下、或者整个堆很紧张时会怎样？**

```
        Evacuation Failure（疏散失败）
    = GC 时【找不到可用的 Region】来安置存活对象
                    ↓
        这些对象只能"就地晋升"到老年代
                    ↓
              老年代被快速填满
                    ↓
        情况继续恶化 → 最终触发 Full GC（停顿长）
```

**Evacuation Failure 是 G1 的性能红灯** —— 出现它说明堆已经非常紧张了。

**怎么查：**

```bash
# GC 日志里搜这两个关键词
grep -E "to-space exhausted|Evacuation Failure" /mydata/logs/gc.log
```

**常见原因与对策：**

| 原因 | 对策 |
|---|---|
| 堆太小 | 调大 `-Xmx` |
| 晋升太快（大量中长期存活对象） | 检查是否有不该长期持有的缓存 / 大对象 |
| Humongous 对象占满 Region | 拆小大对象，或调 `-XX:G1HeapRegionSize` |

### 3.5 所以：不要把 G1 理解成「固定路线」

```
❌ 错误理解（当成固定流水线）
   Eden → S0 → S1 → Old
        每一步都是"指定的那个区域"

✅ 正确理解（角色动态分配）
              ┌──→ Survivor Region
   Eden Region ─┤
              └──→ Old Region

   Young GC：
     选出一批 Young Region
              ↓ Evacuation（复制存活对象）
     新的 Survivor Region / Old Region
              ↓
     原来的 Region 释放，变回「空闲」

   Mixed GC：
     Young Region + 部分 Old Region
              ↓ Evacuation
     释放这些 Region
```

### 3.6 一句话总结

> **G1 在"对象晋升逻辑"上仍然是 Eden → Survivor → Old**（这点和传统 GC 一样），
> 只是把**固定的 Eden/S0/S1/Old 连续空间**改造成了**可以动态分配角色的 Region 集合**；
> 并且 G1 可以在 Young GC 之外，通过 **Mixed GC 增量回收部分 Old Region** ——
> 这是它做到「停顿可预测」的关键。

### ⚠️ G1 下**不要用 `-Xmn`**

老教程里常见的 `-Xmn512m`（写死新生代大小）是 **Parallel / CMS 时代**的做法。

在 G1 下写死 `-Xmn` 会**禁掉 G1 的自适应调优**，反而让性能变差。

**G1 下要控制新生代，用这两种方式：**

| 方式 | 参数 | 说明 |
|---|---|---|
| **设停顿目标**（推荐） | `-XX:MaxGCPauseMillis=200` | 告诉 G1"我最多能接受 200ms 停顿"，它自己反推该给新生代多大 |
| 设比例 | `-XX:NewRatio=2` | 老年代 : 新生代 = 2 : 1 |

> **这也是为什么不要照抄网上的老 JVM 参数** —— 收集器换了，参数语义就变了。
> 很多流传很广的"JVM 调优模板"还是 JDK 8 时代的，套到 JDK 21 上可能起反作用。

## 四、各参数的作用与默认值（JDK 21）

| 参数 | 作用 | JDK 21 默认 | 备注 |
|---|---|---|---|
| `-Xms` | 堆初始大小 | 物理内存 **1/64** | ★ 建议设成和 `-Xmx` 相等 |
| `-Xmx` | 堆最大大小 | 物理内存 **1/4**（容器内是容器内存 1/4） | ★ **生产必须显式指定** |
| `-Xss` | 每个线程栈大小 | 1 MB | 线程多时内存占用 = 线程数 × 此值 |
| `-XX:MetaspaceSize` | 元空间**首次扩容阈值** | 21 MB | 类加载多时会频繁触发 Full GC，可调到 256m |
| `-XX:MaxMetaspaceSize` | 元空间上限 | **无限制** ⚠️ | **生产必须设**，否则类加载泄漏会吃光物理内存 |
| `-XX:MaxDirectMemorySize` | 直接内存上限 | **= `-Xmx`** ⚠️ | NIO/Netty 用，Netty 应用要显式调小 |
| `-XX:+UseG1GC` | 使用 G1 | ✅ 默认开启 | JDK 9+ |
| `-XX:MaxGCPauseMillis` | G1 目标停顿时间 | **200 ms** | 调小 → G1 给新生代更多空间换更少停顿 |
| `-XX:NewRatio` | 老年代:新生代 比例 | 2（老年代占 2/3） | G1 下一般不用动 |
| `-XX:SurvivorRatio` | Eden:S0 比例 | 8（Eden 占 8/10） | |
| `-XX:MaxTenuringThreshold` | 晋升老年代的年龄阈值 | 15 | 对象熬过 15 次 Minor GC 才进老年代 |
| `-XX:G1HeapRegionSize` | G1 Region 大小 | 堆 / 2048（1MB~32MB，2 的幂） | 一般不用动 |
| `-XX:+HeapDumpOnOutOfMemoryError` | OOM 时自动 dump | ❌ 关闭 | ★ 生产必开 |
| `-XX:HeapDumpPath` | dump 文件路径 | 当前目录 | |
| `-XX:+UseZGC` | 使用 ZGC（超低停顿） | ❌ 非默认 | 见下方 |

## 五、可选的垃圾收集器

| 收集器 | 启用参数 | 特点 | 适用场景 |
|---|---|---|---|
| **G1**（默认） | `-XX:+UseG1GC` | 平衡型，停顿可预测（默认目标 200ms） | **大多数场景**，包括本项目 |
| **ZGC** | `-XX:+UseZGC -XX:+ZGenerational` | 超低停顿（< 10ms），但**更吃内存和 CPU** | 大堆（几十 G）+ 极低延迟要求 |
| **Parallel** | `-XX:+UseParallelGC` | 吞吐量优先，停顿长 | 批处理任务，不在意单次停顿 |
| **Serial** | `-XX:+UseSerialGC` | 单线程，停顿长 | 极小内存（几百 MB）、客户端程序 |

> **`-XX:+ZGenerational` 在 JDK 21 是可选开关**（分代 ZGC）；JDK 23+ 已变成 ZGC 的默认行为。

**别轻易换收集器**：如果停顿长是因为**内存泄漏**（老年代一直涨），换 ZGC 只是把问题推后。
该做的堆 dump 分析还是得做（见《性能测试-常见问题手册.md》§2.4.1）。

## 六、常见坑

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 照抄网上的 `-Xmn512m` | G1 自适应失效，性能反而下降 | G1 下用 `-XX:MaxGCPauseMillis` |
| `-Xms` 和 `-Xmx` 不等 | 堆反复扩容 → 频繁 Full GC | 两值相等 |
| 不设 `-XX:MaxMetaspaceSize` | 类加载泄漏时吃光物理内存 | 显式设上限 |
| 容器里不写 `-Xmx` | 只用容器内存 1/4，浪费资源 | 永远显式指定 |
| 堆设成物理内存的 90% | 非堆内存 + OS 没地方放 → 被 OOM Killer 杀 | 堆 ≤ 60~70% |
| `-Xmx4g` 就以为只占 4G | 实际峰值可能 6G+（直接内存默认 = `-Xmx`） | 算总账，不是只算堆 |
| 用 JDK 8 的 GC 日志参数 | `-XX:+PrintGCDetails -Xloggc:` 在 JDK 9 已移除，JDK 21 直接报错 | 用 `-Xlog:gc*:file=...` |
