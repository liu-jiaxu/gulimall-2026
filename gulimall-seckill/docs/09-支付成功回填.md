# 业务流程 09：支付成功回填

## 一、设计思路

- 异步 notify 是支付结果的最终依据；return 只负责把用户带回列表，必须主动查单，不能凭浏览器跳回就改订单状态。
- notify 先验签、再校验 `app_id`，最后按 `trade_status` 处理；非成功状态返回 `success` 停止重试，但不改订单。
- 订单推进用 CAS：`UPDATE oms_order SET status=1 WHERE id=? AND status=0`，与超时关单互斥，重复通知只补支付信息。
- 支付信息按 `order_sn` 唯一维护，存在则更新、不存在则插入，避免重复通知产生多条记录。
- 支付完成后的下游动作彼此独立，失败只记日志，不能把 notify 改成 `failure`，否则支付宝会持续重试已成功的支付。
- 秒杀订单用 `source_type=2` 区分：跳过购物车清理，并实时把 `sms_seckill_order` 从 `BUILT` 条件更新为 `PAID`。
- 已关闭订单的迟到支付不改回已支付，写退款记录并全额退款，退款请求号保证支付宝侧幂等。
- 秒杀回填失败由 `SeckillOrderReconcileTask` 在支付超时后按 order 状态补齐。

关键状态：`oms_order` 的 `0` 待付款、`1` 已支付、`4` 已关闭；`sms_seckill_order` 的 `1` 已建单、`4` 已支付。
关键表：`oms_payment_info` 按 `order_sn` 唯一维护，`oms_refund_info` 记录迟到支付退款。

## 二、主要功能描述

### 触发与前置

- 触发：支付页 `GET /pay/alipay` 生成支付宝表单；支付宝服务器 `POST /pay/notify`；用户浏览器 `GET /pay/return`。
- 前置：订单存在且属于当前会员、`status=0`、`pay_amount>0`；秒杀订单还需 `source_type=2` 且秒杀单为 `BUILT`。

### 处理内容

- 生成电脑网站支付表单，`out_trade_no` 使用 `orderSn`，金额为 `pay_amount`。
- notify/return 验签后把订单 `0→1`，写 `payment_time`、`pay_type=1`，维护 `oms_payment_info`。
- 通知 ware 把锁定库存转为真实扣减，普通订单清理购物车，秒杀订单回填 `PAID`。
- 订单已关闭但支付成功时写退款记录并全额退款，订单保持关闭。

### 不处理内容

- 不创建订单，不动 Redis 秒杀库存和限购计数，不做场次结算。
- 不把已关闭订单改回已支付，不重复扣减库存。
- 支付回调不依赖用户登录态，`/pay/notify` 与 `/pay/return` 需要放行。

### 最终结果

- 正常：`oms_order.status=1`，`oms_payment_info` 一条，ware 工作单 `task_status=3` 且 `stock` 与 `stock_locked` 同减，秒杀单 `status=4`。
- 下游失败：订单仍为已支付；ware 扣减失败需要人工补偿，秒杀回填失败由对账任务补。
- 迟到支付：写 `oms_refund_info` 并调用支付宝退款，订单保持 `status=4`。

| 入口 | 触发方 | 处理依据 |
|---|---|---|
| notify | 支付宝服务器 | 验签、`app_id`、`trade_status`，支付结果最终依据 |
| return | 用户浏览器 | 验签后主动查单，只负责把用户带回列表 |

### 异常与降级

- notify 验签或 `app_id` 校验失败：返回 `failure`，支付宝重试，订单不变。
- 订单不存在、金额不一致、状态非法：`markOrderPaid` 返回 `false`，notify 仍返回 `success`，只记日志。
- 订单已关闭且支付成功：写退款记录并全额退款，订单保持关闭。
- ware 扣减失败：只记日志，没有自动重试任务，库存锁定仍未转扣减。
- seckill 回填失败或购物车删除失败：只记日志，秒杀状态由对账任务补，购物车残留下次清理。

## 三、执行顺序

1. `PayController#pay`：校验 `orderSn`、会员归属和 `status=0`，计算支付剩余秒数并渲染支付页。
2. `PayController#alipayPay`：从 ThreadLocal 取会员，调用 `AlipayService#createPagePayForm`。
3. `AlipayService#createPagePayForm`：校验订单归属、状态和金额，组装 `out_trade_no`、`total_amount`、`FAST_INSTANT_TRADE_PAY`、`30m`。
4. 同上：调用 `AlipayClient#pageExecute` 返回自动提交表单，失败抛 9019。
5. `PayController#alipayNotify`：接收支付宝 POST 参数，调用 `AlipayService#handleNotify`。
6. `AlipayService#handleNotify`：验签失败返回 `failure`；`app_id` 不匹配返回 `failure`。
7. 同上：`trade_status` 不是 `TRADE_SUCCESS` 或 `TRADE_FINISHED` 时返回 `success`，不处理。
8. `OrderServiceImpl#markOrderPaid`：按 `order_sn` 查订单，不存在返回 `false`。
9. 同上：校验 `total_amount` 与 `pay_amount` 一致，不一致返回 `false`。
10. 同上：状态已为 `1` 时补写支付信息并返回 `true`，重复通知幂等。
11. 同上：状态不是 `0` 返回 `false`；条件更新 `status 0→1`、`pay_type=1`、`payment_time=now`。
12. 同上：更新 0 行时重读，已被改为已支付则按幂等返回 `true`，否则返回 `false`。
13. `OrderServiceImpl#saveOrUpdatePaymentInfo`：按 `order_sn` 查 `oms_payment_info`，存在更新、不存在插入，写入交易号与回调内容。
14. `AlipayService#notifyWarePaid` → `WareFeignClient#markPaid` → `WareSkuServiceImpl#deductLockedStock`：按 `order_sn` 找工作单。
15. 同上：`task_status=3` 直接返回；条件更新 `1→3`，0 行抛 `WARE_ORDER_TASK_RELEASED`。
16. 同上：逐条明细同时减 `stock` 与 `stock_locked`（两者都要求足够），`lock_status 1→3`。
17. `AlipayService#clearCartQuietly`：`isSeckillOrder` 为 `true` 直接返回；否则取订单 `skuId` 调用 cart `/deleteCheckedItems`。
18. `CartServiceImpl#deleteCartItems`：对 Redis 购物车 Hash 逐个 `HDEL skuId`。
19. `AlipayService#notifySeckillPaid` → `SeckillOrderInternalController#paid` → `SeckillOrderServiceImpl#markPaid`：条件更新 `BUILT→PAID`。
20. `AlipayService#handleNotify`：`paid=false` 且 `isOrderClosed=true` 时调用 `AlipayRefundService#refundLatePayment`，最终返回 `success`。
21. `AlipayRefundService#refundLatePayment`：校验订单已关闭、金额一致，获取或创建退款记录，未退款成功则调用支付宝全额退款。
22. `PayController#alipayReturn` → `AlipayService#handleReturn`：验签后用 `AlipayTradeQueryRequest` 主动查单，成功则复用 `markOrderPaid` 和下游通知，最后 302 到 `/list.html`。
23. `SeckillOrderReconcileTask#reconcileClosedOrders`：扫 `BUILT` 且超过 `payTimeout+5 分钟` 的单，按 order 状态补释放或回填 `PAID`。
24. 异常分支：notify 处理过程中下游任一步失败只记日志，最终仍返回 `success`，避免支付宝重复回调已成功的订单。
25. 异常分支：return 验签失败或查单失败返回 `null`，`PayController` 仍 302 到列表，订单状态等待 notify 更新。
