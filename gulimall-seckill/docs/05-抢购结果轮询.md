# 业务流程 05：抢购结果轮询

## 一、设计思路

- 结果查询是纯只读链路：只查 `sms_seckill_order`，不写库、不操作秒杀 Redis key、不发 MQ，轮询次数不影响库存。
- 状态由建单流程异步推进：0 待建单、1 已建单、2 已释放、3 建单失败、4 已支付；结果接口只做映射。
- 会员 id 完全取自共享 Session，查询后再次比对 `member_id`；订单不存在与越权统一返回 14008，避免泄露。
- 查询支持 `orderSn` 或 `requestId` 二选一，页面固定使用 `orderSn`；两者都为空返回 14009。
- 前端每秒轮询一次、最多 40 次；`status=1` 跳支付页，`status=3` 展示失败原因并停止。
- `code != 0` 时前端不提示、继续轮询，最终落到超时文案；未登录由拦截器返回 14001。
- 结果接口没有 Sentinel 规则，保护依赖登录校验与数据库连接池；重复轮询只增加数据库读压力。
- 支付页自行校验订单存在、归属与待支付状态，不满足时重定向订单列表。

## 二、主要功能描述

**触发动作**：流程 04 提交成功并拿到 `orderSn` 后，确认页立即开始轮询。

**前置条件**：已登录；`sms_seckill_order` 已存在 `status=0` 的预扣记录；MQ 消费者正在异步建单；浏览器可访问秒杀站点。

**流程职责**：
- 每秒请求 `/seckill/order/result`，最多 40 次。
- 校验登录与订单归属。
- 返回订单当前状态、金额、释放方式与失败原因。
- 按状态跳转支付页或展示失败、超时提示。

**不包含**：
- 不扣库存、不回补库存。
- 不修改订单状态、不重新提交。
- 不调用 order 或 ware 服务，不查 `oms_order`。
- 不展示订单列表，只负责把用户带到支付页。
- 不处理支付。

**结果**：
- `status=1`：跳 `order.gulimall.vip/pay.html?orderSn=...`。
- `status=3`：展示失败原因并停止轮询。
- 其它状态：继续轮询，40 次后提示稍后到订单列表查看。

**状态与写入方**：
- 0 待建单：流程 04 的 `createReservedOrder` 写入。
- 1 已建单：流程 06 建单成功回调写入。
- 2 已释放：释放流程按订单号写入。
- 3 建单失败：流程 06 的 `failAndRelease` 写入并回补库存。
- 4 已支付：支付回调或对账流程写入。

**异常与降级**：
- 未登录或会话过期：拦截器返回 14001，前端静默继续轮询。
- 参数都为空：返回 14009，前端静默继续轮询。
- 订单不存在或不属于当前会员：返回 14008，不泄露订单详情。
- 数据库查询异常：全局异常处理返回错误码，前端静默继续轮询。
- 建单慢于 40 秒：页面提示稍后到订单列表查看，后台继续由 MQ 重试与补偿推进。

**数据与缓存**：
- `sms_seckill_order`：按 `order_sn` 或 `request_id` 只读，`LIMIT 1`。
- Redis Session：拦截器读取 `LOGIN_USER`。
- `seckill:stock:*`、`seckill:user:count:*`、`seckill:reserve:*`、`seckill:release:*`：不读不写。
- `mq_message`：不读不写。

## 三、执行顺序

1. 浏览器：`poll(orderSn)` 启动循环，间隔 1 秒，最多 40 次。
2. Nginx：`GET /seckill/order/result` 命中秒杀站点，转发到 14000，不经过网关。
3. `LoginUserInterceptor#preHandle`：从共享 Session 取 `LOGIN_USER`，放入 ThreadLocal。
4. 未登录：写 HTTP 200 与 `{code:14001}` JSON，不进入 Controller。
5. `SeckillOrderController#result`：接收 `orderSn`、`requestId`，从 ThreadLocal 取会员。
6. `SeckillOrderServiceImpl#getResult`：校验两个参数至少一个非空，否则返回 14009。
7. 按 `order_sn` 或 `request_id` 查询 `sms_seckill_order`，`LIMIT 1`。
8. 记录不存在，或 `member_id` 与当前会员不一致：返回 14008。
9. `SeckillOrderServiceImpl#toResult`：填充 `orderSn`、`status`、`statusText`、`orderId`、`payAmount`、`releaseMode`、`failReason`。
10. `SeckillOrderStatus#text`：把 0 到 4 转成中文状态，未知值返回“未知”。
11. 返回 `R.ok().put("seckillOrder", ...)`，接口全程只有 `SELECT`。
12. 前端 `status == 1`：跳 `orderUrl + '/pay.html?orderSn=...'`，停止轮询。
13. 前端 `status == 3`：展示 `failReason`，停止轮询。
14. 前端 `status == 0`：继续下一秒轮询。
15. 前端 `status == 2` 或 `4`：没有专门分支，继续轮询到 40 次。
16. 响应 `code != 0`：不提示，继续轮询。
17. 网络异常或接口报错：捕获后继续下一轮。
18. 40 次仍未终态：提示“建单处理中，请稍后到订单列表查看”。
19. 跳转支付页后：`PayController#pay` 按 `orderSn` 查询订单。
20. `PayController#pay`：校验订单存在、属于当前会员、状态为待支付，否则重定向 `/list.html`。
21. 校验通过：计算支付剩余时间与分期金额，渲染 `pay` 页面。
