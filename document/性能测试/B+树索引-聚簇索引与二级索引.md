# B+ 树索引：聚簇索引与二级索引

> InnoDB 的索引只有一棵"树"——每张表有且仅有一个**聚簇索引**（主键索引），
> 其余全部是**二级索引**（普通索引）。
>
> 两者最容易混淆的一点是：聚簇索引的键必须唯一，二级索引的键却可以重复。
> 本文用 `pms_category` 表把这件事讲透：**重复值为什么能建索引、怎么查、以及回表是怎么回事**。

---

## 一、核心结论

B+ 树要求的唯一性，约束的是 "用来构建这棵树的键" ，而不是索引列本身。

| 索引类型 | B+ 树的键（Key） | 叶子节点存什么 | 键是否唯一 | 索引列能否重复 |
| :--- | :--- | :--- | :--- | :--- |
| **聚簇索引** | `cat_id`（主键） | **整行数据** | 必须唯一 | 不能 |
| **二级索引** | `(parent_cid, cat_id)` 组合 | **索引列值 + 主键值** | 必须唯一 | **可以重复** |

- 聚簇索引：Key 就是主键本身，因此主键不可重复。
- 二级索引：Key 是 `(索引列, 主键)` 的组合。只要这个**组合**不重复，索引列重复完全没问题。

---

## 二、聚簇索引：叶子节点存整行，所以主键不能重复

聚簇索引的 B+ 树，叶子节点直接存放**完整的一行数据**（InnoDB 中称之为"数据页"）。

假如出现两行 `cat_id = 1` 的记录，那么叶子节点上该放哪一行的完整数据？树的定位结果会产生歧义。因此聚簇索引的键值必须唯一。

### 4 阶 B+ 树示意（聚簇索引）

阶数规则：每个节点最多 4 个孩子（存 3 个键）、至少 2 个孩子（存 1 个键）。

示例数据：

| cat_id | name | parent_cid |
| :---: | :--- | :---: |
| 1 | 手机 | 0 |
| 2 | 电脑 | 0 |
| 3 | 冰箱 | 0 |
| 4 | 苹果 | 1 |
| 5 | 华为 | 1 |
| 6 | 联想 | 2 |

```
                      [ 3 | 5 ]                    ← 根节点（内部节点，只存路由键）
                    /     |     \
                   /      |      \
                  v       v       v
            [ 1 | 2 ]  [ 3 | 4 ]  [ 5 | 6 ]        ← 中间层（内部节点）
           /   |   \  /   |   \  /   |   \
          v    v    v v   v    v v    v    v
       ┌──────────────────────────────────────────┐
 叶子: │ cat_id=1 │ 2 │ 3 │ 4 │ 5 │ 6 │   ...    │  ← 叶子节点存整行数据
       │ 手机 0   │电脑0│冰箱0│苹果1│华为1│联想2│        │
       └──────────────────────────────────────────┘
          └──────┴───┴───┴───┴───┴─────┴──→ 双向链表（有序串联全部叶子）

  内部节点说明：只存用于路由的分隔键，不存真实数据。
```

**查找 `WHERE cat_id = 4`**：从根 `[3|5]` 出发 → 4 落在 3 与 5 之间，走中间分支 → 到 `[3|4]`，4 走右侧分支 → 命中叶子节点，直接拿到整行（苹果，parent_cid=1）。全程**无需回表**。

> 正因叶子存的是整行，主键若重复，树就无法确定该存哪一行 —— 这就是主键必须唯一的根本原因。

---

## 三、二级索引：叶子节点存"索引列+主键"，所以可以重复

给 `parent_cid` 建索引，得到的就是二级索引。它的叶子节点**不存整行数据**，只存 **`parent_cid` 的值 + 该行的主键 `cat_id`**。

三条一级分类的 `parent_cid` 都是 `0`，主键分别是 `1、2、3`：

```
                         [ (0, 3) ]                  ← 根节点（分隔键取左子树最大键）
                        /          \
                       v            v
       ┌───────────────────────┐  ┌───────────────────────┐
 叶子: │ (0,1) │ (0,2) │ (0,3) │→ │ (1,4) │ (1,5) │ (2,6) │  ← 索引页
       └───────────────────────┘  └───────────────────────┘
          叶子节点双向链表 ────────────→

  (注：(0,1) 表示 parent_cid=0, cat_id=1)
```

前三个条目的 `parent_cid` **都是 0（重复了）**，但补上主键后，`(0,1)`、`(0,2)`、`(0,3)` 这个组合就是唯一的。

**关键点**：二级索引**不是无序的**。它的排序规则是——

1. 先按 `parent_cid` 升序；
2. `parent_cid` 相同时，再按主键 `cat_id` 升序。

因此所有 `parent_cid = 0` 的记录在叶子链表中**物理连续**。

---

## 四、`WHERE parent_cid = 0` 的检索过程

### 第一步：树路由，定位起点

从根节点 `(0,3)` 出发，目标键 `0 ≤ (0,3)`，走左分支，到达叶子节点。

### 第二步：顺序扫描，收集全部匹配

定位到第一个 `parent_cid = 0` 的条目 `(0,1)`，然后**沿叶子链表向右扫描**，直到遇到第一个 `parent_cid ≠ 0` 的条目（即 `(1,4)`）停止。

一次性取得三个主键：`1、2、3`。

> 这里正是"重复值怎么快速检索"的答案：**重复值不可怕，无序才可怕**。
> 树路由负责快速定位第一个匹配项，链表负责连续读取剩余匹配项。

### 第三步：回表（Back to Table）

拿着主键 `1、2、3`，回到聚簇索引（`cat_id` 的 B+ 树）分别查出这三行的完整数据。

```
二级索引 idx_parent_cid              聚簇索引（主键）
┌────────────────────┐              ┌────────────────────┐
│  (0,1) → 主键 1 ───┼─────────────→│  cat_id=1 → 整行    │
│  (0,2) → 主键 2 ───┼─────────────→│  cat_id=2 → 整行    │
│  (0,3) → 主键 3 ───┼─────────────→│  cat_id=3 → 整行    │
└────────────────────┘              └────────────────────┘
            这次"拿着主键回主键树取整行"的过程，就叫回表
```

### 覆盖索引：免去回表

若查询字段全部落在二级索引上，例如：

```sql
SELECT cat_id, parent_cid FROM pms_category WHERE parent_cid = 0;
```

所需数据在二级索引的叶子里已经齐了（`parent_cid` + `cat_id`），**无需回表**，直接返回。这就是**覆盖索引**，也是它比 `SELECT *` 更快的原因。

---

## 五、为什么 InnoDB 要这样设计

假如二级索引的叶子节点也直接存整行数据：

- **空间成本高** —— 每建一个索引就要把整张表的数据复制一份；表上 5 个普通索引 = 5 份全量数据。
- **维护成本高** —— 任何一行的更新，都要同步刷新所有索引中的副本。
- **丧失有序链表的价值** —— 叶子节点会变得臃肿，单页能容纳的条目锐减，树迅速增高。

而"索引列 + 主键"的组合键方案同时解决了三件事：

1. **保证 B+ 树键的唯一性**（组合键天然唯一），树结构稳定；
2. **实现普通索引允许重复值**的语义需求；
3. **通过回表按需取整行**，用一次额外的树查找换取巨大的空间节省。

## 六、为什么不用哈希索引

| 对比项 | B+ 树索引 | 哈希索引 |
| :--- | :--- | :--- |
| 等值查询 | O(log N)，约 3~4 次 I/O | O(1) |
| **范围查询** | **支持**（叶子链表顺序扫描） | 不支持 |
| **排序 / ORDER BY** | **天然有序，可避免 filesort** | 不支持 |
| 最左前缀原则 | 支持 | 不支持 |

哈希索引等值查询虽快，但**不支持范围查询、排序和最左前缀**。
B+ 树既能等值查、又能范围查、还能顺便完成排序，因此成为 MySQL 的默认选择。

---

## 七、复杂度与工程结论

- **树路由**：`O(log N)`，B+ 树通常 3~4 层，百万级数据也只需 3~4 次页面访问。
- **扫描匹配**：`O(M)`，`M` 为匹配的记录数，顺序读叶子链表。
- **整体**：`O(log N + M)`。相比全表扫描的 `O(N)`，差距是数量级的。

> 例：100 万条数据中 `parent_cid = 0` 有 10 万条。
> 无索引需全表扫描 100 万行逐行判断；有二级索引则先做 3~4 次树查找定位首条，
> 再沿链表连续读完 10 万条即停。

### 落地建议

1. **主键尽量短**，且用自增或有序 ID。二级索引的叶子要携带主键，主键越长，所有二级索引都越臃肿。
2. **避免 `SELECT *`**。只取所需列，让查询有机会走覆盖索引，省掉回表。
3. **注意回表代价**。若某个查询要从二级索引取回大量行，回表可能变成随机 I/O，此时需评估索引选择性（区分度低的列，如性别、状态位，单列索引收益有限）。
4. **善用组合索引**。`(parent_cid, cat_id)` 这类组合能让 `ORDER BY cat_id` 也直接走索引有序输出。

---

## 附：一句话记忆

- **聚簇索引**：叶子存的是**整行**，所以键（主键）必须唯一。
- **二级索引**：叶子存的是**"索引列 + 主键"的标签**。索引列可以重复，补上主键后组合即唯一；
  查不到整行时，拿主键回聚簇索引取一次，就是**回表**。
