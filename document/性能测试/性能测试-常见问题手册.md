# 性能测试 - 常见问题手册

---

## 一、完整排查案例（测试手册中出现的问题）

### 1.1 现象

JMeter 200 并发压 `/index/catelog.json`：

```
中位数 2260ms，90% 分位 3688ms
```

一个简单查询接口慢了两个数量级。

### 1.2 逐层定位

| 步骤 | 工具 | 发现 | 排除/锁定了什么 |
|---|---|---|---|
| ① | **JMeter** | 均值 2257ms、90% 3688ms、异常 0% | 确认**确实慢**，且**不是错误导致的** |
| ② | **VisualVM Monitor** | CPU 1.2%、GC 0%、堆正常 | **排除** CPU 密集、**排除** 内存/GC 问题 → 判定为"**在等**" |
| ③ | **VisualVM Sampler** | `getCatelogJson` CPU 时间仅 271ms，墙钟 4787ms | **印证**：CPU 时间 << 墙钟时间 = 线程在阻塞等待 |
| ④ | **Arthas trace** | `getAllCategory()` 稳定占 80%~99% | **锁定**瓶颈就在这条 SQL 方法 |
| ⑤ | 看代码 + 配置 | 连接池没配置（HikariCP 默认 `maximum-pool-size=10`）；且分类数据是**典型的热点读数据**，根本不该每次查库 | **找到根因 + 定出优化方向** |

### 1.3 根因分析

```java
// CategoryServiceImpl.java:162
private List<CategoryEntity> getAllCategory() {
    return categoryDao.selectList(
            new LambdaQueryWrapper<CategoryEntity>().eq(CategoryEntity::getShowStatus, 1L));
}
```

**慢的不是 SQL 本身，而是"抢不到数据库连接"：**

```
200 个并发请求
      ↓
都要从这个方法里查数据库
      ↓
HikariCP 连接池默认只有 10 个连接   ← 根因在这
      ↓
190 个线程在池外排队等连接
      ↓
等 1.8 秒才拿到连接 → SQL 本身只跑了几毫秒
```

**这就解释了为什么 CPU 只有 1.2%** —— 线程都在 `wait()`，不消耗 CPU。

> **Arthas trace 显示的是墙钟时间**，它把"等连接"的时间也算进了 `getAllCategory()` 的耗时里。
> 所以看到"某个方法很慢"，**先别急着说这条 SQL 慢** —— 要区分是"执行慢"还是"等待慢"。

### 1.4 优化方案（**必须分层做，只调一个参数没用**）

> ⚠️ **连接池只是"缓解"，不是"治本"。**
> 把池从 10 调到 50，只是让线程少排一会儿队 —— **数据库的压力一点没减少**。
> 真要把 2.2 秒降到几十毫秒，得从下面五层一起下手。

#### 1.4.1 第一层：数据库连接池（立刻见效，成本最低）

```yaml
spring:
  datasource:
    hikari:
      pool-name: GulimallHikariPool
      maximum-pool-size: 50      # 池上限，默认 10
      minimum-idle: 10           # 保底空闲连接，避免冷启动现建
      connection-timeout: 3000   # 等连接超时（毫秒），默认 30000
      idle-timeout: 600000       # 空闲连接多久回收（10 分钟）
      max-lifetime: 1800000      # 连接最大存活（30 分钟）
```

| 参数 | 说明 | 注意事项 |
|---|---|---|
| `maximum-pool-size` | 池里最多几个连接 | **不是越大越好**。① 受 MySQL `max_connections` 限制（默认 151）；② 每个连接在数据库端也占内存；③ 经验值 `CPU核数 × 2 + 磁盘数`，单机 MySQL 配 50 合理 |
| `connection-timeout` | 从池里**拿连接**的超时 | ⚠️ **这不是 SQL 执行超时**！默认 30 秒 = 用户干等 30 秒才报错。设 3 秒可以**快速失败暴露问题** |
| `minimum-idle` | 保持的最小空闲连接 | 默认等于 maximum。调小省资源，但会有"现建连接"的延迟 |
| `max-lifetime` | 连接最大存活时间 | **必须小于 MySQL 的 `wait_timeout`**（默认 28800 秒），否则会拿到服务端已关闭的死连接 |
| `idle-timeout` | 空闲连接回收时间 | 默认 10 分钟 |

> 备选连接池：**Druid**（自带监控面板，能看 SQL 执行统计）、**Tomcat JDBC Pool**。

#### 1.4.2 第二层：Tomcat 工作线程（承接并发）

**Tomcat 线程数和 DB 连接池必须匹配** —— 否则没意义：

```
Tomcat 有 400 个线程，DB 连接池只有 50 个
        ↓
350 个线程拿到请求后，还是卡在"等数据库连接"上
        ↓
换了地方排队而已
```

```yaml
server:
  tomcat:
    threads:
      max: 400                   # 最大工作线程，默认 200
      min-spare: 50              # 最小空闲线程，默认 10
    accept-count: 200            # 队列满了之后还能排队的请求数，默认 100
    max-connections: 10000       # 最大连接数，默认 8192
    connection-timeout: 20000    # 连接建立超时
```

**怎么定：**

- `threads.max` ≈ **连接池上限 × 2~3**（不是每个请求都查 DB，留些余量）
- **不是越大越好**：线程多了上下文切换成本高，内存占用也涨（每线程约 1MB 栈）
- `accept-count` 是排队队列 —— 队列满了之后的新请求直接**被拒绝**（客户端看到 `Connection refused`）。队列太长会让用户等更久，建议别超过 `threads.max`

#### 1.4.3 第三层：加缓存 ★ **这一层才是治本**

**分类数据是典型的"读多写极少"数据** —— 几乎不变，却被高频查询。这种数据**根本不该每次都查数据库**。

**本项目最终落地的是「三级缓存」**，只加 Redis 一层是不够的：

```
请求 ─→ Caffeine(L1, 进程内) ──命中率 ~99.9%──→ 返回（零网络开销）
              │ 未命中（sync=true 只放 1 个线程下去）
              ↓
        Redis(L2, 跨实例共享) ──命中率 ~99%──→ 返回 + 回填 L1
              │ 未命中（分布式锁只放 1 个线程查库）
              ↓
           MySQL(L3)
```

```java
// ① 开启缓存（主启动类）
@EnableCaching
@SpringBootApplication
public class GulimallProductApplication { ... }

// ② 读方法：L1 未命中才会进方法体，方法体里再依次查 L2、抢分布式锁、查 DB
@Cacheable(cacheNames = "catelogJson", key = "'all'", sync = true)
@Override
public Map<String, List<Catelog2Vo>> getCatelogJson() { ... }
```

> **`sync = true` 是关键，不是可选项。**
> L1 里的条目是同一时刻写入、TTL 相同，因此会在同一毫秒集体过期。
> `sync = true` 让 Caffeine 对同一个 key **只放 1 个线程**进去加载，其余线程阻塞等待并复用结果。
> **没有它，10000 个并发请求会全部冲进方法体**，各自查一次 L2、抢一次分布式锁 ——
> 等于 L1 白加了，压力会原样转移到 §2.3.3 那个"超时重试放大"的坑里。

**③ 写方法：清缓存不能用 `@CacheEvict`** ← 本项目实际踩过的坑

| `@CacheEvict` 的问题 | 后果 |
|---|---|
| 只作用于 Spring Cache 抽象（即 **L1**），**清不到 Redis** | L1 清了但 L2 还是旧值，下次查询顺着 L2 命中旧数据。Redis TTL 是 1 天，**等于改了分类一整天不生效**（已实测复现：改名后立即查询仍返回旧名字） |
| 在方法返回时触发，**早于事务 COMMIT** | 这段窗口里读请求会因"缓存已清但 DB 未提交"读到旧值，并把它写回缓存 → 脏数据 |

正确做法是**在事务提交后手动清、且 L1 与 L2 一起清**：

```java
private void evictCacheAfterCommit() {
    if (TransactionSynchronizationManager.isSynchronizationActive()) {
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                evictAllCacheLevels();      // L1(Caffeine) + L2(Redis) 一起清
            }
        });
    } else {
        evictAllCacheLevels();
    }
}
```

> ⚠️ **还有一类漏网之鱼**：`CategoryService extends IService`，`save()` / `updateById()` / `removeById()`
> 这些 MyBatis-Plus 继承来的方法**默认不触发任何缓存清理**。项目里 `CategoryController.save()`
> 就是这么调的。要在实现类里把它们重写一遍补上清缓存（见 `CategoryServiceImpl` 末尾的"写入口收口"）。

> ⚠️ **更新时还要抢同一把分布式锁**：让「更新DB+清缓存」与「查DB+写缓存」互斥，
> 否则查询线程可能把更新前的旧值重新写回缓存。

**Redis 配置要写在 `MyRedissonConfig` 里，不是 yaml**：

```java
// ⚠️ 不要配 spring.data.redis.lettuce.pool —— 它完全不生效，原因见 §2.3.3
single.setAddress("redis://<your-vm-host-ip>:6379");
single.setTimeout(1000);                    // 默认 3000   ┐ 这两个是关键，
single.setRetryAttempts(1);                 // 默认 4      ┘ 否则 P99 会被放大到 13 秒
single.setConnectTimeout(3000);             // 默认 10000
single.setConnectionPoolSize(128);          // 默认 64
single.setConnectionMinimumIdleSize(32);    // 默认 24
single.setIdleConnectionTimeout(30000);     // 默认 10000
```

**Caffeine 那一层配在 yaml**：

```yaml
spring:
  cache:
    type: caffeine
    caffeine:
      spec: maximumSize=100,expireAfterWrite=5m
```

> TTL 取 5min 而不是更短：`sync=true` 下 L1 过期时并发请求会集体阻塞等待一次重载，
> **TTL 越短这种"集体等待"越频繁**（30s 时实测每 30 秒就出现一次）。
> 代价是多实例部署时各节点 L1 有最长 5 分钟的不一致窗口，对分类数据可以接受。

**再加一个启动预热**，把冷启动那一次加载挪出用户请求路径：

```java
@Component
public class CacheWarmUpRunner implements ApplicationRunner {
    @Override
    public void run(ApplicationArguments args) {
        try {
            categoryService.getCatelogJson();     // 启动即预热 L1 + L2
        } catch (Exception e) {
            log.warn("启动预热失败，不影响启动", e);   // 预热失败不能拖垮启动
        }
    }
}
```

**加缓存后要提前想清楚三个经典问题：**

| 问题 | 场景 | 解决 |
|---|---|---|
| **缓存穿透** | 反复查一个**不存在**的 key → 每次都打到 DB | 缓存空值（设短 TTL）；或用布隆过滤器 |
| **缓存击穿** | 某个**热点 key 刚好过期** → 大量请求同时涌向 DB | **两级各挡一次**（见下） |
| **缓存雪崩** | **大批 key 同一时刻集体过期** → DB 瞬间被打满 | TTL 加**随机值**（如 `3600 + random(600)`），错开失效时间 |

**缓存击穿在本项目的两级解法：**

```
L1(Caffeine) 过期的那一瞬间，10000 个请求同时未命中
        ↓
【第一道闸门】@Cacheable(sync = true)
        Caffeine 只放 1 个线程进方法体，其余 9999 个阻塞等待、复用结果
        → Redis 只收到 1 条 GET
        ↓
L2(Redis) 也未命中
        ↓
【第二道闸门】Redisson 分布式锁 catelog-lock
        只放 1 个线程查 DB，其余阻塞
        → MySQL 只被查 1 次
```

> 两道闸门对应两层缓存，缺一不可：
> 只有 L1 的 `sync=true` 挡不住 L2 过期；只有分布式锁则 10000 个线程仍会先冲进方法体打 10000 条 Redis 命令。

> **缓存的取舍**：加缓存会引入"数据一致性"问题（改了库但缓存还没失效）。
> 判断标准是**这个数据能容忍多久的旧值** —— 分类树容忍几秒到几分钟完全没问题，所以缓存是划算的。

#### 1.4.4 第四层：JVM 内存参数

> 📖 **JVM 内存结构、GC 分代模型、JDK 21 的 G1 分区、各参数默认值与取值思路**，
> 详见 **§2.1.1**。这里只给一个能直接用的启动命令。

**默认堆可能很小**（尤其容器里），要显式指定：

```bash
java -Xms1g -Xmx1g \                        # 两值相等，避免堆反复扩容/收缩
     -XX:MetaspaceSize=256m \
     -XX:+HeapDumpOnOutOfMemoryError \       # OOM 时自动 dump，事后能分析
     -XX:HeapDumpPath=/mydata/logs/ \
     -jar gulimall-product-0.0.1-SNAPSHOT.jar \
     > /mydata/logs/product.log 2>&1 &
```

> ⚠️ **容器里跑 Java 特别注意**：Java 10+ 能识别容器内存限制（`UseContainerSupport` 默认开启），
> 但**不显式指定 `-Xmx` 时，默认只有容器内存的 1/4** —— 给容器 4G，JVM 只用 1G，白白浪费。
> 所以**永远显式写 `-Xmx`**。

#### 1.4.5 第五层：SQL 与索引

前面几层都做完了还慢，才轮到怀疑 SQL 本身：

```sql
-- 看执行计划
EXPLAIN SELECT cat_id, name, parent_cid, sort FROM pms_category WHERE show_status = 1;
```

| `type` 值 | 含义 | 要不要处理 |
|---|---|---|
| `const` / `eq_ref` | 走主键/唯一索引 | 很好 |
| `ref` / `range` | 走普通索引 | 正常 |
| `ALL` | **全表扫描** | 看数据量 —— 几百行无所谓，几十万行就要加索引 |

> **注意**：本项目 `pms_category` 只有几百行，**全表扫描本身并不慢**（几毫秒）。
> 所以本次的瓶颈**不是 SQL**，而是"拿不到连接"。**别一看到 ALL 就急着加索引。**

其余常规优化：**显式列出字段别用 `SELECT *`**、**避免深分页**（`LIMIT 100000, 10`）、**批量操作代替循环单条**。

#### 1.4.6 优化优先级

| 层次 | 改动成本 | 收益 | 优先级 |
|---|---|---|---|
| **加缓存（L1 本地 + L2 Redis）** | 低（一个注解 + 配置） | **最高** —— 直接砍掉绝大部分 DB 访问 | ★★★ |
| **Redisson 超时重试参数** | 极低（改配置类） | **高** —— 不加这一项，加缓存反而可能让长尾更差 | ★★★ |
| **数据库连接池** | 极低（改 yaml） | 中 —— 缓解排队 | ★★★ |
| **Tomcat 线程数** | 低 | 中 | ★★ |
| **JVM 内存参数** | 低（改启动命令） | 视情况（内存不足时才明显） | ★★ |
| **SQL / 索引** | 中（要测要验证） | 视数据量 | ★ |

> **顺序建议：先加缓存，再调连接池。**
> 缓存能把 DB 访问量降下来（治本），连接池只是让剩下的请求少排队（治标）。
> 反过来先调池子，DB 压力没变，只是把问题往后推。

> ⚠️ **但"加缓存"不等于"只加 Redis"。** 本项目实测：**只加 Redis 时中位数确实从 2260ms 掉到 8ms，
> P90 却从 3688ms 涨到 10435ms** —— 压力只是从 DB 转移到了 Redis，并没有消失。
> 真正让 P99 达标（18ms）的，是在 Redis 前面又加了一层 Caffeine 本地缓存。
> 详见 §1.5 与 §2.3.3。

### 1.5 优化效果验证（**一层一层改，一层一层压**）

> ⚠️ **不要一次把所有层都改完** —— 那样你不知道是哪个改动起了作用，也说不清每层的收益。
> **正确做法：改一层 → 压一次 → 记录 → 再改下一层。**

| 轮次 | 改了什么 | 中位数 | P99 | 吞吐量 | 异常率 | 说明 |
|---|---|---|---|---|---|---|
| **基线** | 全默认配置 | 2260 ms | (P90 3688) | 40.8 /sec | 0% | 问题确认 |
| 第 1 轮 | + Redis 缓存（Redisson 默认参数） | **8 ms** | **13005 ms** | 14.3 /sec | 0% | ⚠️ **中位数暴跌，长尾却暴涨 3.5 倍** |
| 第 2 轮 | + 收紧 Redisson 超时重试 | 8 ms | 3182 ms | 48.1 /sec | 19% | 长尾降 4 倍，但慢命令开始报错 |
| 第 3 轮 | + 降级兜底（catch 漏了 return） | 10 ms | 9453 ms | 17.6 /sec | 0% | ❌ **反而更差** |
| 第 4 轮 | + 修好 catch、加 GZIP 压缩（66KB→14.7KB） | — | — | — | — | 与下一轮合并测量 |
| 第 5 轮 | **+ Caffeine L1 + 启动预热** | **5 ms** | **18 ms** | **197.2 /sec** | 0% | ★ **P99 达标（要求 <200ms）** |

> **这张表里最重要的不是最终数字，而是第 1 轮和第 3 轮 —— 它们都证明了「加缓存 ≠ 变快」。**

### 三个反直觉的教训

**① 加了缓存，中位数从 2260ms 掉到 8ms，但长尾反而更糟：P90 从 3688ms 涨到 10435ms。**

问题没有消失，只是**从 DB 转移到了 Redis**：

- 原来 200 个线程抢 Hikari 的 10 个连接 → 排队（**等连接**）
- 现在 200 个线程抢 Redis，缓存值 66KB，且 `redisson-spring-boot-starter` 接管后，
  **Redisson 默认的超时重试策略会把一次偶发慢命令放大成 13.5 秒**（详见 §2.3.3）

**② 加了 catch 兜底反而更慢（P99 3023ms → 9453ms）。**

catch 里查了 DB、写了 Redis，**但没有 `return`**，于是继续往下又走了一整轮分布式锁流程
（白等 620ms~2.9s 的锁），而且 200 个线程各查一次 DB，把 Hikari 连接池也打满了。

> **教训**：降级路径一定要确认"拿到数据就返回"。不 return 的 catch，等于把一次失败变成两次开销。

**③ 最终让 P99 达标的，不是"把缓存调大"，而是「把 Redis 从关键路径上挪走」。**

Caffeine L1 命中的请求**根本不产生网络 IO**，Redis 读取退化成低频且无竞争的操作，
超时红线自然不再被撞到 —— 这才是从 3023ms 降到 18ms 的真正原因。
配合 GZIP 压缩（66KB → 14.7KB）进一步降低单次读取耗时，两者叠加才达标。

#### 复测的四条铁律

1. **条件完全一致** —— 线程数、Ramp-Up、循环次数、请求地址都不能变，否则数据没有可比性
2. **先预热再取数** —— 先跑一轮丢弃结果，让 JIT 编译完成、连接池建好连接
3. **压测前重启服务** —— 保证 JVM 状态干净，否则上一轮的 JIT 优化结果会污染对比
4. **至少压 3 轮取中间值** —— 避免偶发抖动造成误判

#### 怎么确认优化真的生效了

**① 看 Redis 缓存命中率**（应该接近 100%）：

```bash
redis-cli info stats | grep -E "keyspace_hits|keyspace_misses"
```

**② 看 MySQL 的查询次数有没有下降**：

```sql
SHOW GLOBAL STATUS LIKE 'Com_select';     -- 压测前后各看一次，对比增量
```

**③ 最有说服力的一条 —— Arthas 看方法还在不在调用链里**：

```bash
trace com.atguigu.gulimall.product.service.impl.CategoryServiceImpl getCatelogJson
```

```
加缓存【前】：getCatelogJson() → getAllCategory()   ← 每次都走 DB
加缓存【后】：getCatelogJson() → （getAllCategory 消失了）
```

**`getAllCategory()` 从调用链里消失，就说明缓存真的生效了** —— 这比看响应时间更直接，
因为它证明的是"**根本没去查库**"，而不是"查得快了一点"。

## 二、常见性能问题分类手册

> 第一章讲的是**其中一种**（数据库连接池）。
> 本章把其它常见问题按类型铺开，每条给出 **现象 → 怎么查 → 怎么改**，当工具书用。

### 2.0 总览：先定位到"哪一类"

| 现象 | 优先怀疑 | 一句话验证方法 |
|---|---|---|
| CPU 打满 | 计算密集 / 死循环 / 正则回溯 | VisualVM Sampler 看谁占 CPU |
| GC 频繁、Full GC 多 | 内存不足 / 内存泄漏 / 临时对象过多 | VisualVM **Visual GC** |
| 内存持续涨不回落 | **对象没被回收**（内存泄漏） | 堆曲线呈"阶梯上升"或"只涨不降" |
| 线程数持续增长 | 线程泄漏 / 阻塞堆积 | VisualVM Monitor 的 Live Threads 曲线 |
| **慢，但 CPU 和 GC 都低** | **在等**（DB / 远程调用 / 锁） | **Arthas `trace`** ★ |
| 吞吐上不去、延迟也不高 | 线程数/连接池不够、压测机瓶颈 | 逐步加并发看拐点 |
| 偶发长尾（99% 远大于中位数） | GC 停顿 / 锁竞争 / 慢 SQL 抖动 / **客户端超时重试放大** | ① 看 GC 日志时间戳与慢请求时间戳是否吻合<br>② 若长尾时长**是个很整齐的值**（如恒定 13 秒），那不是抖动，是**超时重试的算术结果** → 查 §2.3.3 |

### 判断"在算"还是"在等"的通用方法 ★

```
CPU 时间 ÷ 墙钟时间 ≈ 1     →  在算（计算密集型）→ 查代码算法、查火焰图
CPU 时间 ÷ 墙钟时间 << 1    →  在等（阻塞型）    → 查 DB / 远程调用 / 锁
```

本次数据：`271ms CPU / 4787ms 墙钟 ≈ 0.06` → 明确是"在等"。

**这个比值决定了后面所有排查方向**，务必先算出来：

```bash
# 方法一：VisualVM Sampler 直接对比 "Total Time (CPU)" 和 Arthas trace 的墙钟值
# 方法二：Arthas 自带
profiler start
# 压一会儿
profiler stop --format html      # 火焰图：宽的块 = 占 CPU 多
```

### 2.1 服务端配置类（**最容易漏、成本最低，优先查**）

> 很多"性能问题"根本不是代码问题，而是**默认配置太小**。改配置比改代码便宜得多，先查这一层。

#### 2.1.1 JVM 默认内存过小

**现象**：GC 频繁、`OutOfMemoryError: Java heap space`、响应时间随运行时间变长而抖动。

> 📖 **JVM 内存结构、GC 分代模型、JDK 21 的 G1 分区、各参数默认值** →
> 见《JVM内存结构与GC分区.md》。
>
> 本节只留**能直接用的命令**。

**怎么改：三档启动参数参考**

**小内存（测试机，2~4G）**

```bash
java -Xms1g -Xmx1g \
     -XX:MetaspaceSize=128m -XX:MaxMetaspaceSize=256m \
     -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/mydata/logs/ \
     -jar xxx.jar
```

**中等（生产，8G 内存）**

```bash
java -Xms4g -Xmx4g \
     -XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m \
     -XX:MaxDirectMemorySize=512m \
     -XX:MaxGCPauseMillis=200 \
     -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/mydata/logs/ \
     -Xlog:gc*:file=/mydata/logs/gc.log:time,uptime:filecount=10,filesize=50M \
     -jar xxx.jar
```

**大内存 / 极低停顿要求（16G+）**

```bash
java -Xms8g -Xmx8g \
     -XX:+UseZGC -XX:+ZGenerational \
     -XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m \
     -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/mydata/logs/ \
     -jar xxx.jar
```

**JVM 内存参数的三条铁律：**

1. **`-Xms` 和 `-Xmx` 必须相等** —— 否则堆会反复扩容/收缩，每次扩容都触发 Full GC，白送性能损失
2. **`-Xmx` 不要超过物理内存的 50%~70%** —— 剩下的要留给 Metaspace、直接内存、线程栈、操作系统
3. **容器里永远显式写 `-Xmx`** —— Java 10+ 能识别容器限制，但不写时默认只用容器内存的 1/4（给 4G 只用 1G，白白浪费）

**怎么验证参数真的生效了**

```bash
# ① 启动时打印所有最终生效的参数（不启动服务）
java -XX:+PrintFlagsFinal -version | grep -Ei "maxheapsize|initialheapsize|maxmetaspace|useg1gc"

# ② 看运行中的 JVM（Arthas）
jvm
#   输出里能看到 MAX_HEAP_SIZE / InitialHeapSize / 收集器名称等

# ③ 看各代实际使用情况（每 1 秒打印一次，共 10 次）
jstat -gcutil <pid> 1000 10

# ④ VisualVM → Visual GC 面板（最直观，能看 Eden/S0/S1/Old 实时变化）
```

**`jstat -gcutil` 输出怎么读：**

```
  S0     S1     E      O      M     CCS    YGC     YGCT    FGC    FGCT     GCT
  0.00  45.23  62.15  18.30  95.12  92.44   1121    3.973    18    1.026    4.999
         ↑       ↑      ↑                        ↑        ↑       ↑         ↑
     Survivor  Eden  老年代              年轻代GC次数/耗时  Full GC次数/耗时  总GC耗时
```

- **`E` 高、`O` 低、`FGC` 少** → 健康（对象都在新生代被回收了）
- **`O` 持续高位、`FGC` 频繁但回收后 `O` 不降** → **内存泄漏**（见 §2.4.1）
- **`FGCT / GCT` 占总运行时间 > 5%** → GC 开销过大，要调优


#### 2.1.2 Tomcat 连接数 / 线程数不够

**现象**：
- 并发一高就出现 `Connection refused`（队列满了）
- 请求在 Tomcat 层就排队，还没进业务代码
- JMeter 报连接超时

**怎么查**：

```bash
# 看 Tomcat 线程数（http-nio-<port>-exec-* 的数量）
jstack <pid> | grep "http-nio" | wc -l

# Arthas 看线程峰值
dashboard        # 或 thread
```

VisualVM Monitor 的 **Live Threads 曲线**：如果是"顶到某个值就不再涨"（平台期），说明线程池满了。

**怎么改**：

```yaml
server:
  tomcat:
    threads:
      max: 400                   # 默认 200
      min-spare: 50              # 默认 10
    accept-count: 200            # 排队队列，默认 100
    max-connections: 10000       # 默认 8192
    connection-timeout: 20000
```

> ⚠️ **Tomcat 线程数必须和 DB 连接池匹配**：Tomcat 400 线程 + DB 池 50 → 350 个线程还是卡在等连接。
> 参考比例：`threads.max ≈ DB池上限 × 2~3`。

#### 2.1.3 各种连接池没配（不止数据库）

**这是个普遍规律：几乎所有连接池的默认值都偏小。** 高并发下它们会轮流成为瓶颈。

| 连接池 | 默认值 | 建议 | 配置项 |
|---|---|---|---|
| **HikariCP（MySQL）** | 10 | 50 | `spring.datasource.hikari.maximum-pool-size` |
| **Lettuce（Redis）** | 8 | 50 | `spring.data.redis.lettuce.pool.max-active` |
| **Tomcat 线程池** | 200 | 400 | `server.tomcat.threads.max` |
| **Feign/HTTP 连接池** | 依实现而定 | 按下游并发定 | 见 2.6.1 |
| **Nacos 客户端** | — | 一般不用调 | — |

**怎么查**：Arthas `trace` 到某个"等"的方法 → 看它内部是不是在 `getConnection()` / `borrowObject()`。

### 2.2 数据库访问类

#### 2.2.1 连接池太小（★ 本次案例）

**现象**：慢，但 CPU/GC 都低；Arthas trace 显示 DAO 方法耗时占比高。

**怎么查**：
```
Arthas trace 到 DAO 方法 → 占比高，但方法内部"没展开"（是叶子节点）
    ↓ 说明时间花在"等"上，不是"算"上
区分是"等连接"还是"SQL 本身慢"：
    · 看连接池监控（Druid 有面板；Hikari 可开 metrics）
    · 或临时把池调大，看响应时间是否立刻下降 → 下降就是池的问题
```

**怎么改**：见 §1.4.1。

#### 2.2.2 频繁访问 DB / N+1 查询

**现象**：一次请求发几十条 SQL；网络往返次数多；DB QPS 很高但单条 SQL 都不慢。

**怎么查**：

```bash
# ① 开 MyBatis 的 SQL 日志，数一次请求发了几条
mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl

# ② Arthas 统计某个 DAO 方法的调用次数（最直观）
monitor -c 5 com.atguigu.gulimall.product.dao.CategoryDao selectList
#   ↑ 每 5 秒统计一次：调用次数、成功率、平均耗时

# ③ 看 MySQL 的 QPS
SHOW GLOBAL STATUS LIKE 'Questions';
```

**典型的 N+1**（本次代码里就有类似结构）：

```java
// ❌ 循环里查数据库：1000 条数据 = 1000 次查询
for (Long id : ids) {
    CategoryEntity c = categoryDao.selectById(id);   // 每次都打一次 DB
}

// ✅ 一次批量查出来
List<CategoryEntity> list = categoryDao.selectBatchIds(ids);
```

**怎么改**：
- 循环查库 → 改成**批量查询**（`selectBatchIds` / `IN`）
- 频繁查**不变的数据** → 加缓存（见 §2.3）
- 关联查询 → 用 `JOIN` 一次查完，或分两次批量查后在内存里组装

#### 2.2.3 慢 SQL / 缺索引

**现象**：单条 SQL 执行时间就很长（几十毫秒到几秒），且 CPU 也涨（DB 在算）。

**怎么查**：

```sql
-- ① 开慢查询日志（MySQL）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.5;      -- 超过 0.5 秒就记录

-- ② 看执行计划
EXPLAIN SELECT ... FROM pms_category WHERE show_status = 1;
```

| `type` 值 | 含义 | 处理 |
|---|---|---|
| `const` / `eq_ref` | 主键/唯一索引 | 很好 |
| `ref` / `range` | 普通索引 | 正常 |
| `ALL` | **全表扫描** | **看数据量** —— 几百行无所谓，几十万行才要加索引 |
| `index` | 走索引但仍扫全索引 | 一般也需要优化 |

`rows` 列预估扫描行数、`Extra` 里出现 `Using filesort` / `Using temporary` 都值得注意。

**怎么改**：给 WHERE / ORDER BY 的字段加索引；避免索引失效（函数包裹字段、`LIKE '%xx'` 前置通配、隐式类型转换）。

> ⚠️ **别看到 `ALL` 就急着加索引**：`pms_category` 只有几百行，全表扫描只要几毫秒。
> 本次的瓶颈压根不是 SQL。**先确认它真的是瓶颈，再动手。**

#### 2.2.4 长事务 / 锁等待

**现象**：偶发长尾（99% 分位远大于中位数）；日志里有 `Lock wait timeout exceeded`；死锁异常。

**怎么查**：

```sql
-- 看当前有哪些长事务
SELECT * FROM information_schema.INNODB_TRX ORDER BY trx_started;

-- 看锁等待
SELECT * FROM performance_schema.data_lock_waits;

-- MySQL 8.0+ 看锁等待全貌
SELECT * FROM sys.innodb_lock_waits;
```

**怎么改**：
- 事务里**别放远程调用、别放耗时操作**（事务会一直持有锁）
- 缩短事务范围：先查数据、再开事务写
- 加锁顺序保持一致，避免死锁

### 2.3 缓存类

#### 2.3.1 热点数据没缓存（**收益最大的一类**）

**现象**：DB 的 QPS 很高，但读的都是同一批数据；数据几乎不变却每次查库。

**怎么查**：

```bash
# 看 MySQL 到底在忙什么
SHOW GLOBAL STATUS LIKE 'Com_select';         # 总查询次数
SHOW PROCESSLIST;                              # 当前在跑的 SQL

# 判断"读多写少"
#   写：一天改几次？  读：每秒几百次？  → 典型的该缓存
```

**怎么改**：加 Redis 缓存，见 §1.4.3。

**判断该不该缓存的标准**：

| 特征 | 该缓存吗 |
|---|---|
| 读多写极少（分类、品牌、配置） | ✅ 非常适合 |
| 读多写多（库存、点赞数） | ⚠️ 要小心一致性，或只缓存短时间 |
| 数据必须实时（支付状态、余额） | ❌ 不适合缓存，或 TTL 设极短 |

#### 2.3.2 缓存用错反而更慢

| 问题 | 现象 | 解决 |
|---|---|---|
| **缓存大 key** | 单次读取几十 KB，并发下网络 IO = 线程数 × key 大小，易触发 Redis 超时 | ① **GZIP 压缩后存 byte[]**（本项目 66KB → 14.7KB）<br>② **加本地缓存**，把读 Redis 的频率降下来<br>③ 拆分成多个小 key |
| **换了 Redis 客户端** | 原有的连接池/超时配置**静默失效**，且新客户端把偶发慢命令放大 | 打印 `getConnectionFactory().getClass()` 确认底层是谁；配置改到新客户端那边 —— 详见 §2.3.3 |
| **无 TTL** | 数据永不过期，改了就永远不一致 | 必须设 TTL，再加主动失效 |
| **缓存穿透** | 反复查不存在的 key，每次都打 DB | 缓存空值（短 TTL）；布隆过滤器 |
| **缓存击穿** | 热点 key 过期瞬间，大量请求涌向 DB | 两级各挡一次（见 §1.4.3） |
| **缓存雪崩** | 大批 key 同时过期，DB 被打满 | TTL 加随机值 |
| **序列化开销大** | 大对象的 JSON 序列化比查库还慢 | 用更紧凑的序列化（如 Protobuf） |

**怎么查缓存命中率**：

```bash
redis-cli info stats | grep -E "keyspace_hits|keyspace_misses"
# 命中率 = hits / (hits + misses)
# 低于 80% 说明缓存设计有问题（key 太散、TTL 太短、或缓存了不该缓存的）
```

#### 2.3.3 换了 Redis 客户端：配置静默失效 + 超时被放大 ★ 本项目最隐蔽的坑

**现象**：加完 Redis 缓存后，中位数从 2260ms 降到 8ms（看着很正常），
**但 P99 从 3688ms 涨到 13005ms**，而且**异常率 0%** —— 不是报错，纯粹是慢。

根因全在 `pom.xml` 里加的那一个依赖：`redisson-spring-boot-starter`。

##### 坑一：yaml 里的 Redis 配置全部静默失效

```
>>> stringRedisTemplate.getConnectionFactory().getClass().getName()
    = org.redisson.spring.data.connection.RedissonConnectionFactory
```

`redisson-spring-boot-starter` 会用 `RedissonConnectionFactory` **接管** `StringRedisTemplate`。
于是你写的配置和实际生效的完全是两回事：

| 你写在 yaml 里的 | 实际生效的 |
|---|---|
| `spring.data.redis.lettuce.pool.max-active: 50` | **一行都没生效** —— 底层走 Redisson 不是 Lettuce<br>（且 `commons-pool2` 也不在 classpath 上，Spring Boot 本来就不会应用这段配置） |
| `spring.data.redis.timeout: 3s` | Redisson 自己的 `timeout`（默认 3000ms） |

**这个坑最阴的地方是"静默"** —— 配置写在那儿、语法没错、启动无警告，但就是不起作用。
排查压测结果时会一直以为"我明明配了 50 个连接啊"，然后在错误的方向上浪费大量时间。

**验证方法（一行代码）**：

```java
System.out.println(stringRedisTemplate.getConnectionFactory().getClass().getName());
```

##### 坑二：Redisson 默认的"超时 + 重试"把偶发慢命令放大成 13.5 秒

```
默认 timeout = 3000ms、retryAttempts = 4、retryInterval = 1500ms

一个重试周期 = 3000(等超时) + 1500(等间隔) = 4500ms
前 2 次超时后第 3 次成功 = 3000+1500+3000+1500 ≈  9.0s   ← 对应那 30 个 ~10s 的样本
前 3 次超时后第 4 次成功 = 再加 3000+1500        ≈ 13.5s   ← 对应实测最大值 13697ms
```

**关键认知**：**Lettuce 没有这套策略** —— 一个命令慢，它就慢，200ms 后照样返回。
换成 Redisson 后，同一个"偶发慢命令"变成了 13.5 秒的等待。

> **换句话说，"换客户端"这件事本身，就能让 P99 劣化两个数量级** ——
> 和缓存命中率、key 大小、并发数都没关系。

这也解释了 §1.5 第 1 轮那个诡异结果：中位数 8ms（缓存明明在工作），P99 却 13 秒。

##### 怎么改

配置写在 `MyRedissonConfig` 里（**不是 yaml**）：

```java
single.setTimeout(1000);                    // 3000 → 1000，快速失败
single.setRetryAttempts(1);                 // 4 → 1，别放大
single.setConnectTimeout(3000);             // 10000 → 3000
single.setConnectionPoolSize(128);          // 64 → 128
single.setConnectionMinimumIdleSize(32);    // 24 → 32
single.setIdleConnectionTimeout(30000);     // 10000 → 30000
```

**效果**：最坏耗时 **18s → 3.5s**。

> ⚠️ **代价要说清楚**：收紧超时后，原来"卡 10 秒但最终成功"的请求会变成**快速失败抛异常**
> （实测异常率 0% → 19%）。所以这个改动**必须配合降级兜底**（超时 → 直接查 DB）一起做，
> 否则只是把长尾问题换成了错误率问题。

##### 通用教训：引入新依赖时先确认三件事

**引入一个新的客户端 / 中间件依赖时，先确认三件事**：

1. **它有没有偷偷替换掉原有的 Bean？** —— 打印实际类型，别信配置
2. **它的默认参数是什么？** —— 新依赖的默认值是按"通用场景"设计的，未必适合你
3. **它的失败模式是什么？** —— 快速失败还是重试放大？**这直接决定 P99 的量级**

第 1 条只用一行 `getClass().getName()` 就能验证，但**不知道要验证的话，就会一直卡在这儿**。

### 2.4 JVM 内存 / GC 类

#### 2.4.1 对象未回收 → 内存耗尽（内存泄漏）★

**现象**：
- 堆内存曲线**只涨不降**（或"阶梯上升"，Full GC 后也回不到低位）
- 最终 `java.lang.OutOfMemoryError: Java heap space`
- Full GC 越来越频繁，停顿越来越长

**怎么查（三步）**：

**第一步：确认是泄漏还是单纯不够**

VisualVM Monitor 看堆曲线：

```
锯齿状（涨→GC 回落→再涨）    → 正常，只是堆小了点 → 调大 -Xmx 即可
阶梯上升（每次回落点越来越高）→ 泄漏！有对象一直被持有
```

**第二步：抓堆快照**

```bash
# 主动 dump
jmap -dump:live,format=b,file=/mydata/logs/heap.hprof <pid>

# 或者 OOM 时自动 dump（启动时加参数）
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/mydata/logs/

# Arthas 也能 dump
heapdump /mydata/logs/heap.hprof
```

**第三步：用 MAT（Memory Analyzer Tool）分析**

Eclipse MAT 打开 `.hprof` → 看 **Dominator Tree**（支配树）→ 找占用最大的对象 → 看它的 **GC Roots 引用链**（谁持有它不放）。

**常见的泄漏原因：**

| 原因 | 典型代码 | 修法 |
|---|---|---|
| **静态集合只加不减** | `static Map<String, Object> CACHE = new HashMap<>();` 只 put 不 remove | 换成有上限的缓存（Caffeine / Redis），或手动清理 |
| **ThreadLocal 没 remove** | `threadLocal.set(x)` 用完不 `remove()` | **必须放在 `finally` 里 remove**（线程池复用线程时，value 会一直被持有） |
| **监听器/回调没注销** | 注册了 listener 但从不 remove | 生命周期结束时注销 |
| **连接/流没关闭** | `InputStream` / `Connection` 没 close | try-with-resources |
| **本地缓存无上限** | `Map` 当缓存用，key 无限增长 | 设最大容量 + 淘汰策略 |
| **集合里存了大对象** | `List<byte[]>` 不断 add | 及时清理，或用软/弱引用 |

> **本项目要特别注意 `ThreadLocal` 和静态 Map** —— 这是业务代码里最常见的两个泄漏点。

#### 2.4.2 GC 频繁 / Full GC 停顿长

**现象**：偶发长尾延迟；CPU 被 GC 线程吃掉；`GC (Allocation Failure)` 日志刷屏。

**怎么查**：

```bash
# ① GC 统计（每 1 秒打印一次，共 10 次）
jstat -gcutil <pid> 1000 10
#   YGC/YGCT  = 年轻代 GC 次数/总耗时
#   FGC/FGCT  = Full GC 次数/总耗时
#   ★ 重点看 FGCT 占比：超过总运行时间的 5% 就有问题

# ② 开 GC 日志（JDK 21 语法）
-Xlog:gc*:file=/mydata/logs/gc.log:time,uptime:filecount=10,filesize=50M
#   ⚠️ 老写法 -XX:+PrintGCDetails -Xloggc:xxx 在 JDK 9 就被移除了，JDK 21 用会直接报
#      "Unrecognized VM option"

# ③ VisualVM Visual GC 面板最直观
```

**怎么改**：

| 情况 | 处理 |
|---|---|
| 年轻代 GC 频繁但每次都回收干净 | 新生代太小 → **G1 下用 `-XX:MaxGCPauseMillis` 调小停顿目标**让它自己扩（⚠️ **不要用 `-Xmn`**，原因见《JVM内存结构与GC分区.md》§三） |
| Full GC 频繁，回收后老年代仍高 | **内存泄漏**（见 2.4.1）或老年代太小 → 调大 `-Xmx` |
| 单次 Full GC 停顿时长（>1 秒） | 换垃圾收集器：G1 → ZGC（JDK 21 支持，停顿可控制在 10ms 内） |
| 临时对象太多 | 优化代码：减少循环内创建对象、字符串拼接用 `StringBuilder` |

```bash
# JDK 21 用 ZGC（分代 ZGC，停顿可控制在 10ms 内）
java -XX:+UseZGC -XX:+ZGenerational -Xmx4g -jar xxx.jar
#   -XX:+ZGenerational 在 JDK 21 是【可选开关】；JDK 23+ 已变成 ZGC 的默认行为
#   ZGC 代价：占用更多内存、更吃 CPU，适合「大堆 + 低延迟」场景
```

> **换个收集器不是万能的**：GC 停顿长如果是因为**内存泄漏**（老年代一直涨），
> 换 ZGC 只是把问题推后 —— 该 dump 分析还得做（见 §2.4.1）。

### 2.5 线程 / 并发类

#### 2.5.1 自定义线程池配置不当

**现象**：任务堆积、`RejectedExecutionException`、或线程数暴涨。

**典型的错配**：

```java
// ❌ 问题写法：队列无界（LinkedBlockingQueue 默认容量 Integer.MAX_VALUE）
new ThreadPoolExecutor(10, 10, 0L, TimeUnit.MILLISECONDS, new LinkedBlockingQueue<>());
//   → maximumPoolSize 形同虚设，任务无限堆积，最终 OOM

// ✅ 有界队列 + 明确的拒绝策略
new ThreadPoolExecutor(
    10,                                  // 核心线程
    50,                                  // 最大线程
    60L, TimeUnit.SECONDS,               // 空闲存活
    new ArrayBlockingQueue<>(200),       // ★ 有界队列
    new ThreadFactoryBuilder().setNameFormat("gulimall-async-%d").build(),
    new ThreadPoolExecutor.CallerRunsPolicy()   // 拒绝策略：调用方自己执行（起到降速作用）
);
```

**线程池参数怎么定**：

| 任务类型 | 核心线程数 | 理由 |
|---|---|---|
| **CPU 密集** | CPU 核数 + 1 | 多了只是增加切换成本 |
| **IO 密集**（DB、HTTP） | CPU 核数 × 2 ~ 核数 × (1 + 等待时间/计算时间) | 线程大部分时间在等 |

**拒绝策略选择**：

| 策略 | 行为 | 适用 |
|---|---|---|
| `AbortPolicy`（默认） | 抛异常 | 必须知道任务被拒了 |
| `CallerRunsPolicy` | 调用方线程自己跑 | **推荐** —— 起天然的降速作用，不丢任务 |
| `DiscardPolicy` | 静默丢弃 | ⚠️ 危险，会丢数据 |
| `DiscardOldestPolicy` | 丢最老的 | ⚠️ 危险 |

#### 2.5.2 锁竞争

**现象**：CPU 不高但吞吐上不去；`jstack` 里大量线程处于 `BLOCKED`。

**怎么查**：

```bash
# Arthas
thread -b                # ★ 直接找"阻塞其他线程最多的那个"

# 或 jstack 后搜索
jstack <pid> | grep -A 20 "BLOCKED"
```

`thread -b` 是神技 —— 它直接告诉你**谁在锁着别人**。

**怎么改**：
- 缩小锁范围（把耗时的操作挪到锁外）
- 用读写锁 `ReentrantReadWriteLock` 替代互斥锁（读多写少场景）
- 减小锁粒度（分段锁 / `ConcurrentHashMap`）
- 用无锁结构（`Atomic*` 类、`LongAdder`）

#### 2.5.3 线程泄漏

**现象**：Live Threads 数只涨不降；最终 `unable to create native thread`。

**怎么查**：VisualVM Monitor 的线程曲线；Arthas `thread` 看线程名分布（同名线程大量堆积 = 泄漏）。

**常见原因**：每次请求都 `new Thread()`；线程池用完不 `shutdown()`；`Executors.newCachedThreadPool()` 无上限。

### 2.6 远程调用 / 架构类

#### 2.6.1 远程调用超时设置不合理

**现象**：偶发超时；下游慢一点，上游线程全被拖住（雪崩）。

```yaml
# OpenFeign 超时（本项目在 gulimall-common 里配）
spring:
  cloud:
    openfeign:
      client:
        config:
          default:
            connect-timeout: 5000     # 建连超时
            read-timeout: 5000        # ★ 读超时，默认很大（可能一直等）
```

> ⚠️ **读超时太长 = 把上游线程占死**。下游一个接口卡住 30 秒，上游 400 个线程很快被占满，
> 整个服务不可用 —— 这就是**雪崩**。合理设置超时 + 熔断（Sentinel）比调大线程池有用。

#### 2.6.2 串行调用可以改并行

```java
// ❌ 串行：查库存、查优惠、查积分，各 100ms → 总共 300ms
Stock s = stockService.get(skuId);
Coupon c = couponService.get(skuId);
Points p = pointsService.get(userId);

// ✅ 并行：用 CompletableFuture，总共约 100ms
CompletableFuture<Stock>  fs = CompletableFuture.supplyAsync(() -> stockService.get(skuId), executor);
CompletableFuture<Coupon> fc = CompletableFuture.supplyAsync(() -> couponService.get(skuId), executor);
CompletableFuture<Points> fp = CompletableFuture.supplyAsync(() -> pointsService.get(userId), executor);
CompletableFuture.allOf(fs, fc, fp).join();      // 等三个都完成
```

**怎么查**：Arthas trace 看多个远程调用是不是**依次串行**的（一个结束了下一个才开始）。

#### 2.6.3 网关 / Nginx 层

| 项 | 默认 | 说明 |
|---|---|---|
| Nginx `worker_connections` | 1024 | 每个 worker 能处理的最大连接数 |
| Nginx `worker_processes` | auto | = CPU 核数 |
| `client_max_body_size` | 1m | 大文件上传会 413（本项目已改 20m） |
| 网关的线程模型 | WebFlux（非阻塞） | **不要在里面写阻塞代码**，否则整个网关被拖死 |
