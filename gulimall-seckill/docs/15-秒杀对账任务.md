# 业务流程 15：秒杀对账任务

## 一、设计思路

- 五个定时任务按“数据库订单事实为准、最终一致”收敛，允许短暂不一致，由下一轮任务补齐。
- 订单对账先处理 `WAIT_BUILD` 再处理 `BUILT`，先把该建的单建出来，后续支付和关闭对账才有依据。
- 所有状态推进使用条件更新，例如 `order_sn + 旧状态`、`build_retry_count` CAS，保证多实例和重复执行幂等。
- 释放回哪个池取决于场次是否仍为进行中以及库存 key 是否存在；Redis 回补用 `seckill:release:{orderSn}` 做幂等标识。
- 限购 Hash 以 `sms_seckill_order` 中待建单、已建单、已支付的数量为准重建，TTL 优先跟随库存 key。
- 库存对账只读、只告警，不修复，因为库存真相在 ware 的数据库锁定字段，不能凭 Redis 值反推。
- 结算兜底复用 `markEnding` 和 `settleSession`，场次锁加停止中条件更新保证只结算一次。
- MQ 补偿是发送端补偿，用 `mq_message` 记录和 Redisson 锁串行，最多重发 3 次后归档到 `mq_dead_message`。

## 二、主要功能描述

**触发方式**

- 全部由 Spring `@Scheduled` 触发，没有前端页面，也没有手动执行接口。
- `SeckillOrderReconcileTask` 每分钟第 15 秒执行，负责建单、支付和关闭对账。
- `SeckillLimitReconcileTask` 每分钟第 30 秒执行，负责限购 Hash 重建。
- `SeckillStockReconcileTask` 和 `SeckillSettleScheduled` 每天 03:00 执行，分别做库存只读对账和结算兜底。
- `MqMessageCompensateTask` 每分钟第 0 秒执行，负责本地消息表补偿。

**前置条件**

- seckill 和 coupon 启动类开启 `@EnableScheduling`，rabbitmq 公共模块自动配置同样开启定时任务。
- 服务能连接 `gulimall_sms`、Redis 和 RabbitMQ，相关表和队列已创建。
- seckill 能调 order 的内部状态接口，coupon 能调 ware 的释放和刷新接口。

**时间参数与边界**

- 订单对账以秒杀单 `create_time` 为基准，待建单超时 5 分钟，已建单等待“支付超时 + 5 分钟”。
- 支付超时默认复用库存释放延时 30 分钟，结算兜底宽限期同样读取该值。
- 每轮订单对账最多处理 100 条，积压时由后续轮次继续收敛。
- 限购重建与抢购预扣之间没有互斥，只能保证最终一致。

**做什么**

- 订单对账：待建单超时且订单已存在时回填；不存在时重发建单消息，达到 5 次后标记失败并回补库存。
- 已建单超时：订单已关闭时补释放；订单已支付、已发货或已完成时把秒杀单改为已支付。
- 限购重建：按订单事实汇总购买数量，与 `seckill:user:count:{sessionId}:{skuId}` 比较，不一致就删除重建。
- 库存对账：检查库存 key 是否缺失、值是否为数字、是否在 `0 ~ seckill_count` 范围内，只记录告警。
- 结算兜底：补处理停止中超时未结算的场次，以及漏掉结束消息的未开始或进行中场次。
- MQ 补偿：扫描 `mq_message` 中未确认或投递失败的记录，重发或归档。

**不做什么**

- 订单对账不自己创建订单，只查询、重发消息、改秒杀单状态和调用释放接口。
- 限购重建不修改库存 key，不修改 `sms_seckill_order`。
- 库存对账不补 key、不改值、不交叉校验 ware 和订单。
- 结算兜底不处理已支付订单，只释放数据库仍标记为秒杀锁定的剩余库存。
- MQ 补偿不负责消费失败的业务重试，消费失败由 `MqRetryService` 处理。

**结果状态**

- 数据库订单事实、秒杀单状态、Redis 库存与限购、ware 锁定逐步收敛到一致。
- 重复执行不会重复扣减或重复释放；达到重试上限的记录进入死信表等待人工处理。

## 三、执行顺序

1. `SeckillOrderReconcileTask#reconcile`：每分钟第 15 秒依次调用 `reconcileWaitingBuild` 和 `reconcileClosedOrders`。
2. `SeckillOrderReconcileTask#reconcileWaitingBuild`：查 `status=0` 且 `create_time` 早于 5 分钟前的记录，按 id 升序取 100 条。
3. `reconcileWaitingBuild`：逐条调 `OrderFeignClient#getSeckillOrderStatus`；返回成功时调 `SeckillOrderServiceImpl#onBuildSuccess`。
4. `SeckillOrderServiceImpl#onBuildSuccess`：条件更新 `WAIT_BUILD → BUILT`，回填 `order_id` 和 `pay_amount`。
5. `reconcileWaitingBuild`：订单不存在时读取 `build_retry_count`；达到 5 次调 `failAndRelease`，否则调 `resendCreateMessage`。
6. `SeckillOrderReconcileTask#resendCreateMessage`：用 `build_retry_count` 做 CAS 更新，成功后才重发建单消息。
7. `SeckillOrderReconcileTask#resendCreateMessage`：调用 `sendReliable` 投递建单消息，消息同时写入 `mq_message`。
8. `SeckillOrderServiceImpl#failAndRelease`：条件更新 `WAIT_BUILD → BUILD_FAILED` 并写失败原因；成功后回补库存和限购。
9. `SeckillStockServiceImpl#releaseReservation`：Lua 校验 `seckill:release:{orderSn}`，INCRBY 库存、HINCRBY 限购并写释放标识。
10. `SeckillOrderReconcileTask#reconcileClosedOrders`：查 `status=1` 且 `create_time` 早于“支付超时 + 5 分钟”的记录，取 100 条。
11. `reconcileClosedOrders`：订单状态为 4 时调 `releaseByOrderSn`；状态 1~3 时条件更新 `BUILT → PAID`；状态 0 跳过。
12. `SeckillOrderServiceImpl#releaseByOrderSn`：获取场次锁，锁内重查确认仍为已建单，避免重复释放。
13. `SeckillOrderServiceImpl#decideReleaseMode`：场次有效状态为进行中且库存 key 存在时回秒杀池，否则回普通池。
14. `releaseByOrderSn`：调 ware `releaseSeckillOrderStock` 修改 `stock_locked` 和 `seckill_stock_locked`；回秒杀池时再回补 Redis。
15. `releaseByOrderSn`：条件更新 `BUILT → RELEASED`，写入 `release_mode` 和 `release_reason`。
16. `SeckillOrderCreateListener#onCreate`：消费重发消息；预扣记录不存在或状态不是待建单时直接签收，否则调 order 建单。
17. `SeckillLimitReconcileTask#reconcile`：每分钟第 30 秒查当前可售场次及其关联商品。
18. `SeckillLimitReconcileTask#reconcile`：按 `sms_seckill_order` 中待建单、已建单、已支付记录汇总 `session_id:sku_id:member_id` 的数量。
19. `SeckillLimitReconcileTask#reconcile`：与 `seckill:user:count:{sessionId}:{skuId}` 比较，不一致时 DEL 后用 HSET 重建并设置 TTL。
20. `SeckillStockReconcileTask#reconcile`：每天 03:00 扫停止中及未来 3 天的未开始、进行中场次，检查库存 key 存在性和值域。
21. `SeckillSettleScheduled#settleStoppingSessions`：每天 03:00 对宽限期已到的停止中场次调用 `settleSession`。
22. `SeckillSettleScheduled#settleStoppingSessions`：对状态 0/1、已启用且结束时间早于宽限期截止的场次，先 `markEnding` 再 `settleSession`。
23. `MqMessageCompensateTask#resend`：每分钟第 0 秒获取带应用名的 Redisson 锁，调 `resendFailedMessages`。
24. `MqMessageServiceImpl#resendFailedMessages`：扫 `mq_message` 中状态 0/2 且到达重发时间的记录，达到 3 次归档到死信表。
25. `MqMessageServiceImpl#resendFailedMessages`：未达上限时重置状态为 0、重试数加 1，按剩余延时重新投递。
