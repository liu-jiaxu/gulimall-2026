# 秒杀全流程设计思路

## 一、用户端全流程设计思路

1. **秒杀入口与场次展示**：用户从商城首页进入秒杀页，系统按“已启用、未结束、未来三天内开始或正在进行”筛选场次。商品信息优先读 Redis Hash `seckill:session:{sessionId}:skus`，field 是 skuId，value 是商品 JSON 快照，TTL 为场次结束时间加 1 天；`/seckill/sessions`、`/seckill/skus` 各配置 200 QPS 的 Sentinel 流控。缓存缺失时回源 `sms_seckill_session`、`sms_seckill_sku_relation` 和 product，再回填 Hash；product 不可用时跳过该 SKU。  
   （用 Hash 是因为同一场次一次 `HGETALL` 就能取全，value 放 JSON 避免拆很多字段；TTL 跟随场次结束，历史数据自然过期；200 QPS 用来保护数据库和 product 的读流量；回源而不是直接报错，是因为秒杀页允许降级展示。）

2. **商品详情与秒杀信息**：进入商品详情页秒杀模式，展示秒杀价、剩余库存、每人限购和当前会员已购数量。单个商品用 `HGET` 读取 Hash；库存用 String `seckill:stock:{sessionId}:{skuId}`；已购数量用 Hash `seckill:user:count:{sessionId}:{skuId}`，field 是 memberId；`seckillSkuInfo` 资源配置 200 QPS 流控，并按参数索引 1（skuId）配置 20 QPS 热点参数规则；product Feign 配置 fallback；库存 key 缺失时按 0 展示。  
   （单字段 `HGET` 避免整场反序列化；String 适合库存 `DECRBY`，Hash 适合按会员累计购买数；热点参数按 skuId 隔离，防止单个爆款把整个详情接口打满；200 QPS 是接口总闸，20 QPS 是单 SKU 热点闸；fallback 保证 product 故障时页面不返回 500。）

3. **登录态与确认页**：通过 Spring Session 识别登录会员，登录用户存 Redis，namespace 为 `gulimall:session`，cookie 为 `GULIMALLSESSION`，多个子域共享；确认页调用 member Feign 取默认收货地址，按 `min(限购剩余, 库存)` 计算可购数量上限。未登录跳登录页，登录后回跳；无默认地址跳个人中心。  
   （共享 Session 避免每个子域重复登录，Redis 集中存会话支持多实例；数量上限在服务端计算，防止前端改参数绕过限购；默认地址减少用户操作，也避免确认页再选地址带来的库存占用时间。）

4. **抢购前置控制**：提交抢购前先经过 Sentinel：网关 `seckill-route` 100 QPS；抢购资源 `seckillOrderSubmit` 50 QPS；慢调用熔断规则为 10 秒统计窗口、至少 10 次请求、慢调用（超过 800ms）比例超过 50% 时熔断 10 秒。随后校验登录、requestId、参数、随机码、商品快照和时间窗口，前置层被拦截返回 14013，不进入 Redis 扣减。  
   （网关限流挡入口洪峰，方法限流保护 Redis 和数据库，慢调用熔断防止下游变慢拖垮 Tomcat 线程池；先校验再扣减，无效流量不消耗库存；50 QPS、800ms、50% 是开发默认值，生产可按压测结果调整。）

5. **Redis 原子预扣**：Lua 脚本一次操作 4 个 key：String 库存 `seckill:stock:{sessionId}:{skuId}`、Hash 限购 `seckill:user:count:{sessionId}:{skuId}`、String 防重 `seckill:req:{sessionId}:{skuId}:{memberId}`（10 秒，value 为 orderSn）、String 预扣标识 `seckill:reserve:{orderSn}`（30 分钟，value 为 memberId:qty）。脚本内完成时间窗口、库存、限购、防重校验，再执行 `DECRBY`、`HINCRBY`、过期时间设置和预扣标识写入；重复请求返回第一次的 orderSn。  
   （Lua 在 Redis 单线程内原子执行，避免“库存扣了但限购没加”的竞态；一次网络往返完成多次判断，比多条 Redis 命令更快且不会超卖；10 秒防重挡连点，30 分钟预扣标识覆盖建单和第一次对账窗口。）

6. **预扣落库与异步建单**：预扣成功后，在同一个本地事务里写 MySQL `sms_seckill_order`（status=0）和 `mq_message`（status=0）；事务提交后再投递 RabbitMQ `gulimall-seckill-order-exchange`，routingKey 为 `seckill.order.create`，发送端开启 publisher confirm 和 return；确认成功把消息状态置 1，失败或路由失败置 2 等待补偿。抢购接口只返回“排队建单中”。  
   （本地消息表解决“数据库成功、MQ 失败”的消息丢失；`afterCommit` 避免事务未提交就发消息；RabbitMQ 异步解耦，把建单和库存转换从抢购线程移走，起到削峰填谷作用；confirm/return 让发送方知道消息是否真的到达 Broker。）

7. **建单与库存转换**：消费者手动 ack 消费；order 用 Seata AT 的 `@GlobalTransactional` 写 `oms_order`、`oms_order_item`，再调 ware 把 `wms_ware_sku.seckill_stock_locked` 转成 `stock_locked`，写 `wms_ware_order_task`（biz_type=1）；订单号唯一键和条件更新保证幂等；成功把秒杀单 0→1，明确失败 0→3 并回补 Redis，未知异常交给 MQ 重试。  
   （Seata AT 自动记录 undo_log，业务失败整体回滚，避免手写 TCC；活动锁定转订单锁定保证总占用不变；唯一键和条件更新让重复消息不会重复建单；手动 ack 保证异常消息不会被静默丢掉。）

8. **结果轮询与后续状态**：前端按 orderSn 或 requestId 轮询，只允许本人查询；状态为 0 待建单、1 已建单、2 已释放、3 建单失败、4 已支付。取消、超时、支付回调通过内部接口通知秒杀模块；释放时用 Redisson 场次锁 `seckill:settle:lock:{sessionId}`，按场次有效状态和库存 key 是否存在决定回秒杀池还是普通池；释放 Lua 写 `seckill:release:{orderSn}`（7 天）做幂等。  
   （轮询比长连接简单、易排障；本人校验防止越权查单；Redisson 锁避免“判断场次进行中”和“结算删 key”并发冲突；7 天释放标识防延迟消息重复回补；按场次状态决定回池，避免活动结束后把库存写回已删除的秒杀 key。）

9. **异常与最终一致**：消费失败按 10 秒、30 秒、60 秒递增重试，最多 3 次，之后投死信并归档 `mq_dead_message`；本地消息补偿任务每分钟扫描 status=0/2 重发；订单对账 15 秒一次、限购重建 30 秒一次、库存对账和结算兜底每天 3 点；缓存缺失回源，库存 key 缺失按 0，product 不可用降级。  
   （至少一次投递加幂等消费保证最终一致；递增重试给下游恢复时间；死信归档保留现场便于人工重放；定时对账兜住消息丢失、状态未回写和缓存偏差；降级保证依赖故障时秒杀页仍可用。）

## 二、管理端全流程设计思路

1. **活动管理**：管理员通过 renren-fast 后台创建秒杀活动，活动存 MySQL `sms_seckill_promotion`，维护名称、起止时间和上下线状态；后台请求经网关和权限体系访问。活动下存在未结束场次时禁止修改或删除。  
   （活动是场次的父级，父级失效会让场次和库存失控；统一走网关和权限避免绕过管理端；未结束场次保护防止活动被删后库存和延时消息仍在运行。）

2. **场次管理**：场次存 MySQL `sms_seckill_session`，状态字段包括 `status`、`seckill_state`、`settle_type`、`stop_time`。新增或修改时校验起止时间，并按 SKU 检查时间重叠；新增和修改会向 RabbitMQ 注册开始、结束延时消息；状态机为未开始 0→进行中 1→停止中 2→已结束 3 或已取消 4；停止后保留 30 分钟宽限期。  
   （延时消息让状态自动推进，不依赖人工点按钮；时间重叠校验防止同一 SKU 在重叠场次超卖；宽限期给支付和取消留缓冲；状态机配合条件更新，让并发和重复消息有明确结果。）

3. **关联商品管理**：关联记录存 `sms_seckill_sku_relation`，包含 `ware_id`、秒杀价、数量、限购、排序和 version；关联时调 ware 锁 `seckill_stock_locked`，并写 Redis String 库存 key。整个过程使用 Seata 全局事务、Redisson 场次锁；修改数量只在原仓库加减，换商品先释放旧库存再锁新库存；删除时按场次状态决定是否释放。  
   （关联是商品和库存的绑定关系；Seata 保证关联、库存和缓存写入一致；原仓加减避免换仓导致库存漂移；场次锁防止并发修改；version 和 operationId 幂等防重复锁/放库存。）

4. **Redis 上架**：定时任务或手动操作把未来三天和进行中场次商品写入 Redis：商品用 Hash `seckill:session:{sessionId}:skus`，库存用 String `seckill:stock:{sessionId}:{skuId}`；randomCode 沿用旧值；库存 key 用 `setIfAbsent` 只补不覆盖；TTL 为场次结束时间加 1 天；每天 3 点执行，product 不可用时跳过并保留旧缓存。  
   （预热门避免用户请求时集中回源；Hash 适合整场读取，String 适合原子扣减；只补不覆盖防止把已扣库存重置；randomCode 稳定避免页面已发出的随机码失效；TTL 自动清理历史场次。）

5. **场次生命周期驱动**：开始延时消息把场次推进为进行中；结束延时消息把场次推进为停止中并删除秒杀库存 key，立即阻止继续抢购；宽限期到期后结算，按数据库剩余 `seckill_stock_locked` 释放仓储库存、刷新普通可售库存、删除商品 Hash，最后落已结束或已取消。  
   （停止中先删库存 key 是为了立即止损；结算异步执行避免长事务；按数据库剩余锁定释放，不依赖可能已经丢失的 Redis key；刷新普通库存保证活动结束后商品仍可按普通库存销售。）

6. **后台变更与缓存刷新**：场次下架、取消、删除和关联变更共用 Redisson 锁 `seckill:settle:lock:{sessionId}`；库存锁/放使用 `wms_seckill_stock_operation` 的 operationId 唯一索引做幂等；关联表 version 做并发控制；关联变更成功后主动刷新商品 Hash，失败时清理新 key 并恢复旧 key。  
   （锁把场次变更串行化；operationId 唯一索引防止重复锁/放；version 防止并发覆盖；失败时恢复旧缓存，避免数据库、ware 和 Redis 三边不一致。）

7. **运营保障**：Sentinel 规则从 Nacos 动态加载，当前规则为网关 `seckill-route` 100 QPS、抢购 `seckillOrderSubmit` 50 QPS、商品信息 `seckillSkuInfo` 200 QPS、`/seckill/sessions` 200 QPS、`/seckill/skus` 200 QPS、热点参数 20 QPS，慢调用熔断为 800ms、50% 比例、至少 10 次请求、10 秒窗口；秒杀链路接入 Micrometer Tracing + OTLP 到 Jaeger；RabbitMQ 提供重试、死信归档和人工重放；定时对账任务检查库存、限购和订单状态，异常只告警。  
   （Nacos 动态规则不用重启服务；Sentinel 实时保护入口和下游；链路追踪定位跨服务耗时；重试和死信保证消息不丢；对账只告警不自动改业务数据，避免补偿逻辑二次写错。）
